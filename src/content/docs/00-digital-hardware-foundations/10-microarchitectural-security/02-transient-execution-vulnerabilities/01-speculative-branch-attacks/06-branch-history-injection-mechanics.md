# Branch History Injection Mechanics and Global History Register Manipulation

To protect operating system kernels and secure hypervisors against speculative branch target hijacking attacks like Spectre Variant 2, microprocessor manufacturers introduced advanced hardware-enforced branch isolation mechanisms, most notably **Enhanced Indirect Branch Restricted Speculation (eIBRS)**. Under eIBRS, hardware architects modified the CPU's internal Branch Target Buffer (BTB)—the hardware cache responsible for predicting the jump targets of indirect branches—by tagging every BTB entry with its corresponding CPU privilege level (User Mode $PL=3$ versus Kernel Mode $PL=0$) and Process Address Space ID (PCID/ASID). When an unprivileged user process executes in user space, the hardware tags all predictions generated by the user process. When the user process subsequently executes a system call (`syscall`) and transitions into kernel space, the hardware eIBRS boundary checks the privilege tag of every BTB entry. If a BTB entry was created by user-mode code ($PL=3$), the kernel-mode fetch engine ($PL=0$) rejects the prediction, preventing user-space software from poisoning kernel indirect branch targets. Software security engineers believed that eIBRS had permanently solved speculative indirect branch hijacking. However, an un-isolated microarchitectural flaw remained hidden within the branch prediction pipeline: **The Global History Register (GHR)**. To predict conditional and indirect branch outcomes accurately, modern branch predictors do not rely solely on the branch instruction's virtual address; they XOR the branch address with a 32-bit to 194-bit hardware shift register—the Global History Register (also called the Branch History Buffer / BHB)—that records the precise sequence of Taken ($1$) and Not-Taken ($0$) outcomes of all recently executed branches. Crucially, while hardware architects tagged target entries in the BTB under eIBRS, **they did NOT isolate or clear the Global History Register across privilege transitions!** An unprivileged user-space process can execute a precise sequence of artificial conditional branches in user mode to craft an arbitrary binary pattern inside the shared GHR. When the process transitions into kernel mode, the GHR retains the attacker's manipulated history pattern. When the kernel executes an indirect branch, the manipulated GHR forces the predictor to calculate a prediction table index that collides with an existing, valid kernel-mode target entry pointing to an attacker-selected disclosure gadget. This vulnerability, known as **Branch History Injection (BHI)** or **Spectre-BHB**, proves that tagging BTB target entries is insufficient if the global branch history register used to index those entries remains un-isolated across security domains.

## Predictor Architecture: TAGE, Gshare, and the Global History Register

To understand why the Global History Register is shared and how it interacts with branch prediction lookup tables, we must inspect the internal microarchitecture of modern CPU branch predictors.

### Why Branch Predictors Use Global History

In early processors, branch predictors evaluated each branch instruction independently based solely on that branch's own past outcomes (Bimodal Prediction).

However, in complex software algorithms, the direction of a branch is frequently **correlated with the outcomes of completely different branches** executed earlier in the program flow.

Consider this simple software example:

```c
// Correlated Branch Execution Example
if (x == 0) {       // Branch 1
    do_something();
}
if (y == 0) {       // Branch 2
    do_other();
}
if (x + y == 0) {   // Branch 3 (Correlated with Branch 1 AND Branch 2!)
    // Branch 3 is TAKEN IF AND ONLY IF Branch 1 was TAKEN AND Branch 2 was TAKEN!
}
```

Notice Branch 3:
If the CPU knows that Branch 1 was **TAKEN** ($x = 0$) and Branch 2 was **TAKEN** ($y = 0$), the CPU can predict Branch 3 with $100\%$ accuracy!

To capture these inter-branch correlations, hardware architects introduced the **Global History Register (GHR)**.


### Gshare and TAGE Prediction Table Indexing

In advanced branch predictors (such as **Gshare** or **TAGE - TAgged GEometric History Length** predictors), the CPU predicts the target of an indirect branch by combining the branch's virtual instruction address ($A_{\text{branch}}$) with the Global History Register ($\text{GHR}$).

The lookup index ($I_{\text{table}}$) into the Branch Target Buffer or Pattern History Table is calculated using bitwise XOR hashing:

$$\mathbf{I_{\text{table}} = (A_{\text{branch}} \gg \text{Shift}) \ \mathbf{\oplus} \ \text{GHR} \ \ \mathbf{\&} \ \ (N_{\text{entries}} - 1)}$$

Where:
* $I_{\text{table}}$ is the integer index ($0 \dots N_{\text{entries}}-1$) selecting a specific prediction slot.
* $A_{\text{branch}}$ is the 64-bit virtual instruction address of the indirect branch.
* $\text{GHR}$ is the current 64-bit binary vector stored in the Global History Register.
* $\oplus$ is the bitwise XOR operator.
* $N_{\text{entries}}$ is the total number of slots in the prediction table (e.g., $N_{\text{entries}} = 4,096 = 2^{12}$).

```text
GSHARE / TAGE HARDWARE INDEXING DATAPATH

 Virtual Address of Branch (A_branch)
 ┌─────────────────────────────────────────────────────────────┐
 │ Extract Lower Bits [15:4]                                   │
 └─────────────┬───────────────────────────────────────────────┘
               │
               ├───────────────────► [ Bitwise XOR Gate ]
               │                            ▲
 Global History Register (GHR) ─────────────┘
 (Contains Attacker's Manipulated Pattern!) │
                                            ▼
                                  Table Lookup Index I_table
                                            │
                                            ▼
                       Selects Prediction Entry in Hardware Table!
```

Look at the indexing equation:
The lookup index $I_{\text{table}}$ depends on **BOTH $A_{\text{branch}}$ AND $\text{GHR}$**!

Even if $A_{\text{branch}}$ is fixed and protected by eIBRS, **changing the bits in $\text{GHR}$ alters $I_{\text{table}}$ completely**!


### The Fundamental Flaw: The Un-Isolated GHR

Why does eIBRS fail to prevent Branch History Injection?

Because eIBRS tags **only the BTB entries**! eIBRS does **NOT** tag or isolate the Global History Register ($\text{GHR}$)!

```text
THE EIBRS SECURITY GAP

 ┌─────────────────────────────────────────────────────────────┐
 │ EIBRS HARDWARE PROTECTION (BTB Entries)                     │
 │  * BTB Target Entries ARE TAGGED with PL=0 vs PL=3.         │
 │  * User Mode PL=3 CANNOT create a valid PL=0 BTB entry!     │
 ├─────────────────────────────────────────────────────────────┤
 │ UN-PROTECTED GHR SHIFT REGISTER                             │
 │  * Global History Register IS NOT TAGGED!                   │
 │  * User Mode PL=3 CAN MANIPULATE the shared GHR bits!       │
 └─────────────────────────────────────────────────────────────┘
  (Attacker uses GHR manipulation to collide with EXISTING kernel BTB entries!)
```

Trace the flaw in eIBRS:
1. An attacker running in User Mode ($PL=3$) cannot create a new BTB entry marked $PL=0$.
2. **BUT THE KERNEL ALREADY CONTAINS VALID $PL=0$ BTB ENTRIES!** The kernel binary contains thousands of legitimate $PL=0$ BTB entries created during prior kernel execution!
3. Among these thousands of legitimate kernel BTB entries sits a valid $PL=0$ entry pointing to a **Kernel Disclosure Gadget ($A_{\text{gadget}}$)**.
4. By executing a calculated sequence of branches in User Mode ($PL=3$), the attacker manipulates the shared $\text{GHR}$ so that when the kernel executes an indirect branch at $A_{\text{kernel}}$, the XOR sum $A_{\text{kernel}} \oplus \text{GHR}_{\text{manipulated}}$ **collides with the index of the existing kernel gadget entry!**
5. The BTB reads the entry at that collided index. The entry's tag matches $\text{PL}=0$ (because it was created by the kernel earlier!).
6. **eIBRS Tag Check PASSES!** The CPU speculatively jumps to the kernel gadget!

The attacker bypassed eIBRS without ever creating a fake $PL=0$ entry, purely by **steering the kernel's index lookup to an existing kernel entry via GHR manipulation!**


### Step-by-Step Hardware Datapath Walkthrough:

#### Step 1: Target Index Engineering
The attacker selects a target kernel indirect branch $A_{\text{kernel}}$ and identifies an existing kernel BTB entry pointing to a disclosure gadget $A_{\text{gadget}}$ located at table index $I_{\text{target}}$.

The attacker calculates the required $64\text{-bit}$ history pattern ($\text{GHR}_{\text{target}}$) that satisfies:

$$\mathbf{(A_{\text{kernel}} \gg \text{Shift}) \ \mathbf{\oplus} \ \text{GHR}_{\text{target}} \ \ \mathbf{\&} \ \ (N_{\text{entries}} - 1) == I_{\text{target}}}$$

Solving for $\text{GHR}_{\text{target}}$:

$$\mathbf{\text{GHR}_{\text{target}} = (A_{\text{kernel}} \gg \text{Shift}) \ \mathbf{\oplus} \ I_{\text{target}}}$$


#### Step 3: Triggering the Kernel System Call
Immediately after completing the GHR manipulation loop, the attacker executes a system call (`syscall` or `int 0x80`):
1. The CPU context-switches from User Mode ($PL=3$) to Kernel Mode ($PL=0$).
2. **The Un-Isolated GHR Persistence**: The physical GHR shift register **retains $\text{GHR}_{\text{target}}$** across the privilege boundary!


## Hardware and Software Mitigations

Because Branch History Injection bypasses early eIBRS hardware isolation, CPU foundries and operating system developers implemented two major mitigation layers: **Software BHB Clearing** and **Hardware History Isolation (ARM CSV2.2 / Intel eIBRS Extensions)**.

```text
BHI MITIGATION TAXONOMY

                          BHI MITIGATION STRATEGIES
                                      │
         ┌────────────────────────────┴────────────────────────────┐
         ▼                                                         ▼
 SOFTWARE BHB CLEARING LOOP (Software)             HARDWARE HISTORY ISOLATION (Silicon)
 * Overwrites GHR with 32/64 dummy branches        * Hardware automatically clears or tags GHR
   on every kernel entry (syscall/interrupt).        on privilege transitions (PL3 -> PL0).
```


### Mitigation 2: Hardware History Isolation (ARM CSV2.2 / Intel eIBRS Extensions)

In newer CPU microarchitectures (ARMv8.5-A+ with CSV2.2/CSV2.3 and modern Intel/AMD processors):
* **Hardware GHR Reset on Privilege Transition**: The CPU hardware automatically **clears or resets the physical GHR shift register to zero** whenever the execution privilege level transitions from $PL=3$ (User) to $PL=0$ (Kernel).
* **Zero Software Overhead**: Hardware resets the GHR in **$1\text{ clock cycle}$** during the `syscall` context switch, eliminating the software BHB clearing loop and restoring $100\%$ bare-metal system call performance!


### Scenario and Parameters

You are a principal microarchitectural security engineer auditing a $3.2\text{ GHz}$ 64-bit server processor core ($T_{\text{clk}} = 0.3125\text{ ns} = 312.5\text{ ps}$).

The processor operates an Advanced Gshare Branch Predictor with the following parameters:
* **Prediction Table Capacity**: $N_{\text{entries}} = 4,096\text{ slots}$ ($2^{12} = 4,096 \implies 12\text{-bit Index}$).
* **Global History Register (GHR) Width**: $32\text{ Bits}$.
* **Index Hashing Formula**:
  $$I_{\text{table}} = (A_{\text{branch}}[15:4]) \ \mathbf{\oplus} \ \text{GHR}[11:0]$$
* **Hardware eIBRS**: Enabled (Tags BTB entries with $PL=0$ vs $PL=3$).

```text
3.2 GHz SERVER PROCESSOR WITH GSHARE PREDICTOR & eIBRS

 User Attacker Process (PL = 3) ──► [ Gshare Predictor (12-bit Index) ] ──► Kernel Syscall (PL = 0)
 Clock T = 312.5 ps                  Index = A_branch[15:4] XOR GHR[11:0]   Kernel Branch @ 0x8140_1040
```

#### Memory Addresses:
* Kernel Indirect Branch Address: $A_{\text{kernel}} = \mathbf{\text{0xFFFFFFFF\_8140\_1040}}$.

3. Trace the clock cycle execution timeline ($t_0 \dots t_4$) when the kernel executes $A_{\text{kernel}}$ with $\text{GHR}_{\text{pattern}}$ active:

6. Verify mathematical, structural, and timing correctness.


#### Step 2: Trace Speculative Execution Timeline

1. **Cycle 0 ($t = 0.0\text{ ns}$)**: Kernel executes indirect branch at $A_{\text{kernel}} = \text{0xFFFFFFFF\_8140\_1040}$. Function pointer misses in cache $\implies$ Memory read issued to DRAM ($T_{\text{DRAM\_miss}} = 160\text{ cycles}$).
2. **Cycle 1 ($t = 0.3125\text{ ns}$)**: Predictor XORs address `0x104` with $\text{GHR} = \text{0x027}$, calculating $I_{\text{lookup}} = \text{0x123}$.
3. **Cycle 2 ($t = 0.6250\text{ ns}$)**: Predictor fetches Entry `0x123` from prediction table $\implies$ Target $= \mathbf{\text{0xFFFFFFFF\_8100\_9000} \quad (A_{\text{gadget}})}$.
   * **eIBRS Privilege Check**: Entry `0x123` has $\text{Tag}_{\text{PL}} = 0$ (created by kernel previously!) $\implies$ **eIBRS CHECK PASSES!**
4. **Cycle 3 ($t = 0.9375\text{ ns}$)**: CPU **speculatively jumps to $A_{\text{gadget}}$ in Kernel Mode ($PL=0$)**!
5. **Cycle 5 ($t = 1.5625\text{ ns}$)**: Gadget executes `mov rax, [rdi]`. Reads kernel secret byte $S = 77_{10} = \text{0x4D} = \text{'M'}$.
6. **Cycle 8 ($t = 2.5000\text{ ns}$)**: Gadget executes `mov rbx, [rax*64 + rsi]`. Dispatches load for probe line `T[77 * 64]`.
7. **Cycle 44 ($t = 13.7500\text{ ns}$)**: Line `T[77]` is fetched from L3 into L1 Data Cache.
8. **Cycle 160 ($t = 50.0000\text{ ns}$)**: Kernel function pointer arrives from DRAM (`0xFFFFFFFF_8105_2000`).
   * Misprediction detected! ($\text{Real Target } \text{0x8105\_2000} \neq \text{Predicted Target } \text{0x8100\_9000}$).
   * **ROB FLUSH FIRED!** Pipeline flushed. Registers reset.
   * **Line `T[77]` remains resident in L1 Data Cache!**

$$\text{Line Fill Complete Time } (44\text{ cycles}) \le \text{ROB Flush Time } (160\text{ cycles}) \quad (\mathbf{\text{SPECULATIVE LEAKAGE PASSED!}})$$


#### Step 4: Verify Software BHB Clearing Mitigation

Now, suppose the Linux kernel executes a **BHB Clearing Loop** (32 dummy branches) on `syscall` entry:

##### 1. GHR State after BHB Clearing Loop:
The 32 dummy branch outcomes overwrite the GHR, setting $\text{GHR}_{\text{cleared}} = \mathbf{\text{0x000}}$.

##### 2. Recalculate Prediction Table Index ($I_{\text{safe}}$):

$$I_{\text{safe}} = A_{\text{kernel}}[15:4] \ \mathbf{\oplus} \ \text{GHR}_{\text{cleared}} = \text{0x104} \ \mathbf{\oplus} \ \text{0x000} = \mathbf{\text{0x104}}$$

##### 3. Security Outcome:
* $I_{\text{safe}} \, (\text{0x104}) \neq I_{\text{target}} \, (\text{0x123})$.
* The predictor queries Entry `0x104`, which points to the legitimate kernel function target `0x8105_2000`.
* **THE BHI ATTACK IS $100\%$ NEUTRALIZED!** Attacker's gadget $A_{\text{gadget}}$ is **NEVER** executed!

##### 4. Calculate Execution Time Penalty of BHB Clearing Loop:
Executing 32 dummy branches ($1\text{ cycle}$ per branch) plus loop overhead ($16\text{ cycles}$ total):

$$\text{Cycles}_{\text{BHB\_clearing}} = 32 + 16 = \mathbf{48 \text{ CPU Clock Cycles}}$$

In physical nanoseconds ($T_{\text{clk}} = 0.3125\text{ ns}$):

$$\Delta T_{\text{BHB\_clearing\_ns}} = 48 \times 0.3125 \text{ ns} = \mathbf{15.0 \text{ Nanoseconds}}$$

## Key Output Primitives

This lesson formally delivers the following conceptual primitives to your digital logic engineering toolbox:

* **Branch History Injection (BHI)**: A transient execution vulnerability where an unprivileged attacker process executes a sequence of conditional branches in user space to manipulate the un-isolated Global History Register (GHR), forcing kernel indirect branches to calculate index collisions that speculatively jump to kernel disclosure gadgets, bypassing eIBRS hardware isolation.
* **Global history register manipulation**: The microarchitectural technique of intentionally shifting specific Taken/Not-Taken branch outcomes into the shared hardware GHR shift register to control the XOR index lookup calculation of prediction tables in higher-privilege contexts.
