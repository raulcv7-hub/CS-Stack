# Application Binary Interface (ABI) Register Contracts: Caller-Saved versus Callee-Saved Register Preservation Mechanics

## The Register Corruption Chaos: Why Subroutines Overwrite Shared State

In a modern multi-gigahertz central processing unit (CPU), software execution relies on a single, shared hardware structure called the **Architectural Register File**. In a 64-bit RISC architecture (such as RISC-V RV64I), this register file consists of 32 physical 64-bit registers ($x0 \dots x31$) located directly adjacent to the Arithmetic Logic Unit (ALU). These registers serve as high-speed SRAM storage cells that hold working variables, loop counters, memory address pointers, and mathematical results, delivering data operands to execution pipelines in a single clock cycle ($0.3125\text{ nanoseconds}$ at $3.2\text{ GHz}$).

However, when software is compiled into modular subroutines (functions), every single function in the entire program—from the main entry point to a tiny string-length helper function—must execute its calculations using **this exact same set of 32 physical hardware registers**.

This shared hardware resource creates a critical microarchitectural conflict: **The Register Corruption Hazard**.

Consider what occurs when a caller function (`main()`) holds an active loop counter ($i = 100$) inside register `x10` and executes a subroutine call (`call process_item`):

```text
THE REGISTER CORRUPTION HAZARD

 Caller Function (main)                       Callee Subroutine (process_item)
 ┌────────────────────────────────────────┐   ┌──────────────────────────────┐
 │ Holds Loop Counter i = 100 in Reg x10  │   │ Needs a scratchpad register! │
 ├────────────────────────────────────────┤   ├──────────────────────────────┤
 │ Executes: call process_item            ├──►│ Executes: addi x10, x0, 42   │
 │   (Jumps to process_item)              │   │   (Overwrites x10 with 42!)  │
 │                                        │   │ Executes: ret                │
 │ Resumes Execution:                     │◄──┴──────────────────────────────┘
 │ Reads x10 expecting 100, finds 42!     │
 │ (LOOP STATE DESTROYED! CPU CRASHES!)   │
 └────────────────────────────────────────┘
```

Trace the physical hardware failure step-by-step:
1. **Pre-Call State**: Function `main()` uses register `x10` to track its loop iteration ($100$).
2. **Subroutine Jump**: Function `main()` executes `call process_item`. Execution jumps to `process_item`.
3. **Local Overwrite**: Function `process_item` needs a scratchpad register to calculate a local value. Unaware that `main()` was using `x10`, `process_item` executes `addi x10, x0, 42`, writing $42$ into physical register `x10`.
4. **Subroutine Return**: Function `process_item` finishes and executes `ret`. Execution returns to `main()`.
5. **State Corruption**: Function `main()` attempts to execute its next loop iteration by reading register `x10`. Instead of finding its loop counter ($100$), it reads $42$! 

Function `main()`'s loop control is completely corrupted, resulting in wrong arithmetic calculations, premature loop terminations, or infinite execution crashes!

---

### The Naive Solution: The "Save Everything" Memory Bottleneck

How can we prevent subroutines from corrupting each other's register data?

A naive hardware approach would be to force the CPU to **save all 32 architectural registers onto the stack before every function call**, and restore all 32 registers after every function call:

```riscv
# NAIVE "SAVE EVERYTHING" FUNCTION CALL (EXTREME MEMORY WASTAGE)

# Before calling function:
sd x1, 0(sp);  sd x2, 8(sp);  sd x3, 16(sp) ... sd x31, 240(sp) # 31 Memory Stores!
call process_item
ld x1, 0(sp);  ld x2, 8(sp);  ld x3, 16(sp) ... ld x31, 240(sp) # 31 Memory Loads!
```

Look at the catastrophic memory traffic generated by this naive approach:
* Every single function call in the program requires executing **31 memory store instructions** before the call, and **31 memory load instructions** after the call!
* A simple function call that performs a 1-cycle addition would require **62 off-chip or cache memory operations** just to save and restore registers!
* Level 1 Data Caches would be completely flooded with register save traffic, memory bandwidth would be consumed by redundant stores, and software execution speed would collapse by over $90\%$.

We are trapped in a fundamental system design dilemma:
* If functions do not save registers, they corrupt each other's data and crash the system.
* If functions save *all* registers on every call, memory bandwidth is exhausted, and execution speed collapses.

To resolve this dilemma, software and hardware systems enforce a standardized contract that partitions the architectural register file into two distinct duty groups: **Application Binary Interface (ABI) Register Preservation Contracts**, defining **Caller-Saved (Volatile)** and **Callee-Saved (Non-Volatile)** registers.

```text
 Shared Workbench (32 Tool Slots: Registers x0..x31)
 ┌─────────────────────────────┬─────────────────────────────┐

 │ (Slots 5..7, 10..17, 28..31)│ (Slots 1..2, 8..9, 18..27)  │
 └─────────────────────────────┴─────────────────────────────┘
  ◄── Caller-Saved / Volatile ─► ◄── Callee-Saved / Preserved ─►
```

The workshop contains **32 physical tool slots** mounted on a central workbench (**The 32 Architectural Registers $x0 \dots x31$**). 

Carpenter A is working on a complex, multi-day dining table project. Carpenter A needs to pause their work and ask Carpenter B to step in and drill a quick hole in a wooden board (**Execute a Subroutine Call**).

To prevent Carpenter B from misplacing Carpenter A's fine chisels and measuring tapes, the workshop manager establishes a strict **Workshop Rulebook (The ABI Contract)** that divides the 32 tool slots into two clear categories:

* **The Rulebook Definition**: Public Scratchpad slots are designated as temporary, shared workspaces.
* **Carpenter B's Privilege (Callee)**: When Carpenter B steps up to the workbench to drill the hole, Carpenter B has **full permission to use any Public Scratchpad slot and leave whatever tools or mess they want in those slots when finished**! Carpenter B is NOT required to clean up or restore Public Scratchpad slots!
* **Carpenter A's Duty (Caller-Saved)**: Carpenter A knows that Carpenter B will likely mess up the Public Scratchpad slots. Therefore, if Carpenter A has a valuable measurement sitting in a Public Scratchpad slot that they will need *after* Carpenter B finishes, **Carpenter A MUST put that measurement away into their personal backpack (The Call Stack Frame) BEFORE calling Carpenter B**!
* If Carpenter A leaves a measurement in a Public Scratchpad slot and Carpenter B overwrites it, **it is Carpenter A's own fault** for breaking the rulebook!

---

### Category 2: Reserved Lockbox Slots (Callee-Saved / Non-Volatile Registers)

* **The Rulebook Definition**: Reserved Lockbox slots are designated as long-term preserved storage.
* **Carpenter A's Privilege (Caller)**: Carpenter A can leave their most valuable tools and measurements in Reserved Lockbox slots with complete peace of mind, knowing that these slots will remain $100\%$ untouched across Carpenter B's work shift. Carpenter A does **NOT** need to pack these items into their backpack before calling Carpenter B!
* **Carpenter B's Duty (Callee-Saved)**: Carpenter B is allowed to use a Reserved Lockbox slot *if* they run out of scratchpad space. **BUT before placing anything into a Reserved Lockbox slot, Carpenter B MUST take Carpenter A's item out, store it on a temporary shelf (The Call Stack Frame), and MUST restore Carpenter A's item EXACTLY as found before walking away!**

```text
WORKSHOP ABI RULEBOOK SUMMARY

 1. Public Scratchpads (Caller-Saved / Volatile):
    * Carpenter B (Callee) can overwrite freely WITHOUT restoring!
    * Carpenter A (Caller) MUST save to backpack BEFORE calling if needed later!

 2. Reserved Lockboxes (Callee-Saved / Non-Volatile / Preserved):
    * Carpenter B (Callee) MUST save to shelf & restore original item if used!
    * Carpenter A (Caller) can leave items here safely across calls WITHOUT saving!
```

Look at what this Workshop Rulebook achieves:

1. **Zero Unnecessary Packing**: Carpenter B does not waste time packing and unpacking all 32 tool slots! If Carpenter B needs only 2 tools to drill a hole, Carpenter B uses 2 Public Scratchpad slots and does **zero packing work**!
2. **Clear Separation of Responsibility**: Carpenter A knows exactly which scratchpad slots need saving before making a call, and Carpenter B knows exactly which lockbox slots must be restored before returning.
3. **Flawless Interoperability**: Carpenter A and Carpenter B can be from different countries and speak different languages (compiled by different compilers or written by different developers), but as long as both follow the Workshop Rulebook, their code integrates with **$100\%$ zero register data corruption**!

This Workshop Rulebook is the exact physical analogue of **Application Binary Interface (ABI) Register Preservation**:
* Carpenter A is **The Caller Function (`main()`)**.
* Carpenter B is **The Callee Subroutine (`process_item()`)**.
* The 32 workbench tool slots are **Architectural Registers ($x0 \dots x31$)**.
* Public Scratchpads are **Caller-Saved / Volatile Registers (`t0`–`t6`, `a0`–`a7`)**.
* Reserved Lockboxes are **Callee-Saved / Non-Volatile Registers (`s0`–`s11`, `sp`, `ra`)**.
* The personal backpack / storage shelf is **The Call Stack Frame in RAM**.

## Primitive 1: Application Binary Interface (ABI) Register Contracts

Now that we possess an intuitive mental model of shared workshop tool benches and lockbox slots, let us examine the formal, rigorous engineering mechanics of an **Application Binary Interface (ABI)**.

> **An Application Binary Interface (ABI)** is a low-level architectural specification that defines the binary-level contract between compiled software modules. It specifies register preservation duties (caller-saved vs. callee-saved), function parameter passing conventions, return value register assignments, stack alignment rules, and data structure byte layouts across a specific CPU architecture.

Without an ABI, code compiled by GCC could not call libraries compiled by Clang, and high-level languages like Rust or Python could not invoke low-level C assembly routines.

---

### The RISC-V 32-Register ABI Classification Map

In the standard 64-bit RISC-V ABI (LP64D / RV64I), the 32 general-purpose architectural registers ($x0 \dots x31$) are partitioned into specific functional roles and preservation contracts:

```text
RISC-V ARCHITECTURAL REGISTER ABI CLASSIFICATION MAP

 Reg Name │ ABI Name │ Saver Duty   │ Primary ABI Functional Role
──────────┼──────────┼──────────────┼─────────────────────────────────────────────────
 x0       │ zero     │ None         │ Hardwired Zero Constant (Immutable)
 x1       │ ra       │ Callee-Saved │ Return Address Pointer (Saved if non-leaf!)
 x2       │ sp       │ Callee-Saved │ Stack Pointer (Points to top of Call Stack)
 x3       │ gp       │ Read-Only    │ Global Pointer (Base address of .sdata)
 x4       │ tp       │ Read-Only    │ Thread Pointer (Base address of TLS)
 x5 - x7  │ t0 - t2  │ Caller-Saved │ Temporary Scratchpad Registers
 x8 - x9  │ s0 - s1  │ Callee-Saved │ Frame Pointer (s0/fp) & Saved Register s1
 x10 - x11│ a0 - a1  │ Caller-Saved │ Function Argument 0..1 & Return Values 0..1
 x12 - x17│ a2 - a7  │ Caller-Saved │ Function Arguments 2..7
 x18 - x27│ s2 - s11 │ Callee-Saved │ Saved Registers (Long-term local variables)
 x28 - x31│ t3 - t6  │ Caller-Saved │ Temporary Scratchpad Registers
```

Let us analyze the three operational register categories defined by the ABI:

---

### 1. Caller-Saved (Volatile / Scratchpad) Registers

* **ABI Designations**: Temporary registers **`t0`–`t6`** ($x5 \dots x7, x28 \dots x31$) and Argument registers **`a0`–`a7`** ($x10 \dots x17$).
* **Preservation Rule**: **The Callee is FREE TO OVERWRITE these registers without saving or restoring them!**
* **Caller's Responsibility**:
  * If the caller function holds a live variable inside a caller-saved register (`t0`–`t6` or `a0`–`a7`) that it will need *after* a subroutine call returns, **the caller MUST save that register onto its stack frame before issuing `call`**, and reload it from the stack after `call` completes!
  * If the caller does *not* need the value after the call, the caller does nothing, avoiding unnecessary memory traffic!

```riscv
# CALLER-SAVED REGISTER PRESERVATION PATTERN (INSIDE CALLER MAIN)

# Caller holds an active variable in volatile register t0 before calling a function:
sd   t0, 0(sp)        # 1. CALLER SAVES t0 onto its stack frame BEFORE call!
call process_data     # 2. Subroutine executes (process_data WILL overwrite t0!)
ld   t0, 0(sp)        # 3. CALLER RESTORES t0 from stack frame AFTER call!
```

---

### 2. Callee-Saved (Non-Volatile / Preserved) Registers

* **ABI Designations**: Saved registers **`s0`–`s11`** ($x8 \dots x9, x18 \dots x27$), Stack Pointer **`sp`** ($x2$), and Return Address **`ra`** ($x1$).
* **Preservation Rule**: **The Callee MUST GUARANTEE that these registers contain their exact original values upon function return (`ret`)!**
* **Callee's Responsibility**:
  * If a subroutine (callee) uses any callee-saved register (`s0`–`s11`, `ra`) to perform its own internal calculations, **the callee MUST save the original value onto its stack frame in its function prologue**, and restore the original value from the stack in its function epilogue before executing `ret`!
  * The caller function can leave active variables inside `s0`–`s11` across function calls with $100\%$ confidence, knowing the callee will never ruin them!

```riscv
# CALLEE-SAVED REGISTER PRESERVATION PATTERN (INSIDE CALLEE SUBROUTINE)

process_data:
    # --- FUNCTION PROLOGUE ---
    addi sp, sp, -16   # Allocate stack frame
    sd   s0, 0(sp)     # 1. CALLEE SAVES s0 in prologue before using it!

    # --- FUNCTION BODY ---
    addi s0, x10, 42   # Callee uses s0 freely for local math

    # --- FUNCTION EPILOGUE ---
    ld   s0, 0(sp)     # 2. CALLEE RESTORES original s0 before returning!
    addi sp, sp, 16    # Deallocate stack frame
    ret                # 3. Returns to caller with s0 100% UNTOUCHED!
```

---

### 3. Read-Only / Constant Registers

* **ABI Designations**: Hardwired Zero **`zero`** ($x0$), Global Pointer **`gp`** ($x3$), and Thread Pointer **`tp`** ($x4$).
* **Preservation Rule**: These registers hold global execution anchors. Subroutines are **STRICTLY FORBIDDEN** from writing to `gp` or `tp` during normal execution. Because they are constant across function calls, neither caller nor callee ever needs to save or restore them on the stack!

## Primitive 2: Caller-Saved versus Callee-Saved Execution Mechanics

To master assembly language programming, let us trace how the caller-saved and callee-saved rules interact during a real-world multi-function execution flow.

### Complete Execution Trace of a Two-Function Call

Consider a scenario where function `main()` (Caller) holds two active local variables:
* A short-lived loop counter $i = 10$ stored in volatile register **`t0`** (Caller-Saved).
* A long-term running total $sum = 500$ stored in non-volatile register **`s0`** (Callee-Saved).

Function `main()` calls subroutine `compute_square()` (Callee), which needs to use registers `t0` and `s0` for its own internal math:

```text
CALLER-SAVED VS CALLEE-SAVED FULL EXECUTION TRACE

 CALLER (main) SIDE                           CALLEE (compute_square) SIDE
 ┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
 │ t0 = 10 (Volatile loop counter)      │     │                                      │
 │ s0 = 500 (Non-volatile running total)│     │                                      │
 ├──────────────────────────────────────┤     │                                      │
 │ 1. Save t0 to stack (sd t0, 0(sp))   │     │                                      │
 │ 2. Issue `call compute_square`       ├────►│ 3. Prologue: Save s0 to stack     │
 │                                      │     │    (sd s0, 0(sp))                    │
 │                                      │     │ 4. Overwrites t0 = 999 (Free!)       │
 │                                      │     │ 5. Overwrites s0 = 888 (Must restore)│
 │                                      │     │ 6. Epilogue: Restore s0 from stack   │
 │                                      │     │    (ld s0, 0(sp))                    │
 │ 8. Restore t0 from stack (ld t0, 0)  │◄────┤ 7. Execute `ret`                     │
 ├──────────────────────────────────────┤     └──────────────────────────────────────┘
 │ t0 = 10 (Restored by main!)          │
 │ s0 = 500 (Restored by compute_sq!)   │
 └──────────────────────────────────────┘
  (Both variables preserved with ZERO data corruption and MINIMAL stack traffic!)
```

Let us trace the physical execution step-by-step:

#### Step 1: Caller-Side Preparation (`main()`)
1. `main()` wants to preserve $i = 10$ (stored in `t0`) across the call. Because `t0` is **Caller-Saved**, `main()` executes `sd t0, 0(sp)` to save `t0` onto its stack frame.
2. `main()` wants to preserve $sum = 500$ (stored in `s0`) across the call. Because `s0` is **Callee-Saved**, `main()` **DOES NOT SAVE `s0`**! `main()` leaves `s0` in its register slot with zero stack memory writes.
3. `main()` executes `call compute_square`.

#### Step 2: Callee-Side Execution (`compute_square()`)
1. **Prologue**: `compute_square` plans to use `s0` for its internal math. Because `s0` is **Callee-Saved**, `compute_square` executes `sd s0, 0(sp)` in its prologue to save `main()`'s $500$ onto its own stack frame!
2. **Body**: `compute_square` uses `t0` freely ($t0 \Leftarrow 999$), overwriting `main()`'s old value. `compute_square` uses `s0` freely ($s0 \Leftarrow 888$).
3. **Epilogue**: Before returning, `compute_square` executes `ld s0, 0(sp)` to restore $s0 \Leftarrow 500$.
4. `compute_square` executes `ret`.

#### Step 3: Caller-Side Resume (`main()`)
1. `main()` resumes execution immediately after the `call` instruction.
2. `main()` reads `s0`: it contains **$500$** (restored by `compute_square`!).
3. `main()` executes `ld t0, 0(sp)` to reload $t0 \Leftarrow 10$ from its stack frame.
4. Both variables $i = 10$ and $sum = 500$ are $100\%$ intact!

## Real-World Silicon Engineering: Leaf Function Optimizations and Stack Bandwidth Reduction

In commercial software development and high-performance compiler engineering (such as GCC or Clang compiling with `-O3` optimization flags), understanding ABI register contracts allows compilers to achieve massive memory bandwidth reductions:

### 1. Leaf Function Register Optimization

In software architectures, a **Leaf Function** is a subroutine that performs calculations **WITHOUT calling any other subroutines**. A leaf function sits at the tip of the execution call tree.

How do optimizing compilers utilize ABI register contracts when generating code for a leaf function?

> **The Leaf Function Register Optimization Rule**: An optimizing compiler assigns all local variables inside a leaf function EXCLUSIVELY to **Caller-Saved / Temporary Registers (`t0`–`t6`, `a0`–`a7`)**!

```riscv
# OPTIMIZED LEAF FUNCTION (ZERO STACK ALLOCATION & ZERO MEMORY WRITES)

# C Source: int32_t add_and_square(int32_t x, int32_t y) { return (x + y) * (x + y); }

.global add_and_square
add_and_square:
    # ZERO PROLOGUE! NO STACK ALLOCATION (addi sp, sp, -16 OMITTED!)
    # ZERO STACK STORES! (sd s0, 0(sp) OMITTED!)
    
    add  t0, a0, a1      # t0 <= x + y (Uses volatile temporary t0!)
    mul  a0, t0, t0      # a0 <= (x + y) * (x + y) (Returns result in a0!)
    
    # ZERO EPILOGUE! NO STACK LOADS!
    ret                  # Returns in 1 CLOCK CYCLE!
```

Look at the extraordinary microarchitectural performance of this optimized leaf function:
* The function executes in **3 clock cycles** ($0.9375\text{ ns}$ at $3.2\text{ GHz}$).
* It uses only temporary registers (`t0`, `a0`, `a1`).
* **It executes ZERO stack memory allocations (`addi sp`), ZERO stack stores (`sd`), and ZERO stack loads (`ld`)**!

By utilizing caller-saved temporary registers, the leaf function runs entirely inside high-speed SRAM registers at $100\%$ pure pipeline speed, consuming **zero memory interconnect bandwidth**!

---

### 2. Quantifying Memory Bandwidth Savings of ABI Partitioning

Why did computer architects divide registers into Caller-Saved and Callee-Saved groups instead of making all registers Caller-Saved or all registers Callee-Saved?

Let us mathematically quantify the memory traffic saved by ABI register partitioning across a typical application executing 1,000,000 function calls:

```text
ABI PARTITIONING MEMORY TRAFFIC SAVINGS

 Policy 1: Save All 32 Registers on Every Call
 1,000,000 Calls x 62 Memory Ops (31 Stores + 31 Loads) = 62,000,000 Memory Ops!
 Total Memory Traffic = 62,000,000 x 8 Bytes = 496 MEGABYTES of Bus Traffic!

 Policy 2: ABI Partitioned Registers (Caller-Saved vs Callee-Saved)
 Average Function uses 2 Volatile + 2 Non-Volatile Registers:
 1,000,000 Calls x 4 Memory Ops (2 Stores + 2 Loads) = 4,000,000 Memory Ops!
 Total Memory Traffic = 4,000,000 x 8 Bytes = 32 MEGABYTES of Bus Traffic!
 (93.5% REDUCTION IN OFF-CHIP MEMORY TRAFFIC!)
```

#### Mathematical Result:
ABI register partitioning reduces function call memory traffic from **$496\text{ Megabytes}$ down to $32\text{ Megabytes}$**—a **$93.5\%$ reduction in memory bus traffic**!

By balancing register preservation duties between caller and callee, modern software executes with minimal stack memory overhead.

### Step-by-Step Derivation

---

#### Step 1: Perform the ABI Register Duty Audit

Let us evaluate the preservation duties for each function according to RISC-V ABI rules:

##### 1. `main_caller()` Audit:
* Holds active variable $i$ in `t0` (Caller-Saved / Volatile).
  * Duty: Since `main_caller()` needs `t0` after `process_data()` returns, **`main_caller()` MUST save `t0` onto its stack frame BEFORE issuing `call process_data`**!

* Calls `compute_checksum()` $\implies$ **Return Address `ra` MUST BE SAVED on stack**!
* Uses temporary `t0` (Caller-Saved / Volatile):
  * Duty: `process_data()` can overwrite `t0` freely **WITHOUT saving it in its prologue**!
* Uses saved registers `s0` and `s1` (Callee-Saved / Non-Volatile):
  * Duty: Because `process_data()` modifies `s0` and `s1`, **`process_data()` MUST save `s0` and `s1` onto its stack frame in its prologue**, and restore them in its epilogue!

* Uses ONLY argument registers (`a0`, `a1`) and temporary registers (`t0`, `t1`).
* All used registers (`a0`, `a1`, `t0`, `t1`) are **Caller-Saved / Volatile**!
* Does NOT call any other function $\implies$ `ra` is NOT overwritten!
* **Leaf Function Optimization**: `compute_checksum()` saves **ZERO REGISTERS ON THE STACK**! Prologue and epilogue are $100\%$ empty!

```text
ABI REGISTER DUTY AUDIT SUMMARY

 Function Name      │ Role     │ Registers Saved by Caller │ Registers Saved by Callee Prologue
────────────────────┼──────────┼───────────────────────────┼────────────────────────────────────
 main_caller()      │ Caller   │ t0 (1 Register)           │ -
 process_data()     │ Non-Leaf │ None (before compute_ch)  │ ra, s0, s1 (3 Registers)
```

#### Step 2: Write Assembly Prologues, Call Sites, and Epilogues

##### 1. Assembly for `main_caller()` (Caller Side):
```riscv
# MAIN_CALLER (CALLER SIDE)
    addi sp, sp, -16       # 1. Allocate 16 bytes on stack (16B aligned!)
    sd   t0, 0(sp)         # 2. SAVE volatile t0 before call
    call process_data      # 3. Call non-leaf subroutine
    ld   t0, 0(sp)         # 4. RESTORE volatile t0 after call
    addi sp, sp, 16        # 5. Deallocate stack
```

##### 2. Assembly for `process_data()` (Callee / Non-Leaf Side):
`process_data` saves 3 registers (`ra`, `s0`, `s1`). To maintain 16-byte stack alignment ($sp \pmod{16} == 0$), it allocates **32 bytes** on the stack ($4 \times 8\text{ bytes}$):

```riscv
# PROCESS_DATA (NON-LEAF SUBROUTINE)
.global process_data
process_data:
    # --- PROLOGUE ---
    addi sp, sp, -32       # Allocate 32 bytes (16-byte aligned!)
    sd   ra, 0(sp)         # Save return address ra
    sd   s0, 8(sp)         # Save callee-saved s0
    sd   s1, 16(sp)        # Save callee-saved s1

    # --- BODY ---
    # ... Uses t0 freely without saving! ...
    # ... Uses s0, s1 across call ...
    call compute_checksum  # Calls leaf function (ra overwritten, but saved at 0(sp)!)

    # --- EPILOGUE ---
    ld   ra, 0(sp)         # Restore ra
    ld   s0, 8(sp)         # Restore s0
    ld   s1, 16(sp)        # Restore s1
    addi sp, sp, 32        # Deallocate stack
    ret                    # Return to main_caller()
```

##### 3. Assembly for `compute_checksum()` (Optimized Leaf Function):
```riscv
# COMPUTE_CHECKSUM (OPTIMIZED LEAF SUBROUTINE)
.global compute_checksum
compute_checksum:
    # ZERO PROLOGUE! NO STACK ALLOCATION NEEDED!
    add  t0, a0, a1        # Uses temporary registers freely
    xor  a0, t0, t1        # Returns result in a0
    # ZERO EPILOGUE!
    ret                    # Returns instantly in 1 cycle!
```

#### Step 3: Calculate Memory Operations and Stack Traffic Volume

Let us count the total memory stack operations (stores and loads) executed during one complete call chain `main_caller()` $\to$ `process_data()` $\to$ `compute_checksum()` $\to$ `process_data()` $\to$ `main_caller()`:

##### Case A: Naive "Save All 31 Registers" Policy
Under a naive policy, every function call saves all 31 general-purpose registers (`x1`..`x31`):
* `main_caller` calls `process_data`: 31 stores + 31 loads = $62\text{ ops}$.
* `process_data` calls `compute_checksum`: 31 stores + 31 loads = $62\text{ ops}$.

$$\text{Total Memory Ops (Case A)} = 62 + 62 = \mathbf{124 \text{ Memory Operations}}$$

$$\text{Total Stack Memory Traffic (Case A)} = 124 \text{ ops} \times 8 \text{ bytes/op} = \mathbf{992 \text{ Bytes}}$$

##### Case B: Optimized ABI Partitioned Policy
Under our optimized ABI design:
* `main_caller` saves `t0`: 1 store + 1 load = $2\text{ ops}$.
* `process_data` saves `ra, s0, s1`: 3 stores + 3 loads = $6\text{ ops}$.
* `compute_checksum` saves nothing (Leaf Optimization): $0\text{ ops}$.

$$\text{Total Memory Ops (Case B)} = 2 + 6 + 0 = \mathbf{8 \text{ Memory Operations}}$$

$$\text{Total Stack Memory Traffic (Case B)} = 8 \text{ ops} \times 8 \text{ bytes/op} = \mathbf{64 \text{ Bytes}}$$

$$\text{Traffic Reduction} = (1 - 0.0645) \times 100\% = \mathbf{93.55\% \text{ Stack Memory Traffic Reduction!}}$$

## Key Output Primitives

This lesson formally delivers the following conceptual primitives to your digital logic engineering toolbox:

* **Application Binary Interface (ABI)**: The low-level binary contract that governs register preservation duties, parameter-passing conventions (`a0`–`a7`), and stack alignment invariants across compiled software modules.
* **Caller-Saved Registers (Volatile)**: Registers (`t0`–`t6`, `a0`–`a7`) that a subroutine is permitted to overwrite freely without restoring, requiring the caller to save them onto its stack frame before a `call` instruction if their values are needed later.
* **Callee-Saved Registers (Non-Volatile / Preserved)**: Registers (`s0`–`s11`, `sp`, `ra`) whose values MUST be preserved across function calls, requiring a subroutine that uses them to save their original values onto its stack frame in its prologue and restore them in its epilogue before executing `ret`.
