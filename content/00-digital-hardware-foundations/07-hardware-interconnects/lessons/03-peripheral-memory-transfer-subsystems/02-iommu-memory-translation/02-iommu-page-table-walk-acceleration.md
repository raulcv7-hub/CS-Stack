# IOMMU Page Table Walk Mechanics and IOTLB Translation Cache Acceleration

## The Multi-Level Page Walk Memory Latency Penalty in Peripheral Streaming

In high-performance multi-core System-on-Chip (SoC) architectures, high-speed peripheral expansion devices—such as $100\text{-Gigabit}$ Ethernet network cards, NVMe solid-state storage arrays, and neural network accelerators—stream massive amounts of data into and out of main system RAM using Direct Memory Access (DMA) transactions across the interconnect.

To enforce memory security, prevent rogue peripheral attacks, and support virtualized multi-tenant cloud environments, every incoming DMA transaction passes through an **Input-Output Memory Management Unit (IOMMU)**. 

The IOMMU intercepts the IO Virtual Address ($\text{IOVA}$) generated by the peripheral device and translates it into an actual physical DRAM address ($\text{PA}$) before handing the data write or read request to the main DRAM memory controller.

However, in 64-bit computer architectures, physical system memory is mapped using **Multi-Level Page Tables** stored directly in main DRAM memory. To translate a single 64-bit $\text{IOVA}$ address without hardware acceleration, the IOMMU must execute a **4-Level Page Table Walk** across four hierarchical page directory tables stored in DRAM: `PML4` $\to$ `PDPT` $\to$ `PD` $\to$ `PT`.

Now, trace the catastrophic physical memory latency penalty that occurs when a high-speed peripheral device dispatches an un-accelerated DMA write transaction across the interconnect:

```text
THE 4-LEVEL UN-ACCELERATED IOMMU PAGE WALK LATENCY PENALTY

 Incoming DMA Packet Write to IOVA = 0x42000
                       │
                       ▼
 1. Read PML4 Directory Entry from DRAM ──────► [ DRAM Read 1: 120 Cycles (37.5 ns) ]
 2. Read PDPT Directory Entry from DRAM ──────► [ DRAM Read 2: 120 Cycles (37.5 ns) ]
 3. Read PD Directory Entry from DRAM   ──────► [ DRAM Read 3: 120 Cycles (37.5 ns) ]
 4. Read PT Page Table Entry from DRAM  ──────► [ DRAM Read 4: 120 Cycles (37.5 ns) ]
                       │
                       ▼ Physical Address PA = 0x9000 Finally Translated!
 5. Execute Actual DMA Packet Write to DRAM ──► [ DRAM Write : 120 Cycles (37.5 ns) ]
 (4 Preliminary DRAM Reads required just to translate ONE single DMA packet address!)
```

Examine this physical hardware breakdown:
1. **DRAM Read 1 (PML4 Lookup)**: The IOMMU reads the Level 4 Page Map entry from DRAM. The IOMMU sits frozen for **$120\text{ CPU clock cycles}$ ($37.5\text{ nanoseconds}$)** waiting for off-chip DRAM.
2. **DRAM Read 2 (PDPT Lookup)**: The IOMMU reads the Level 3 Page Directory Pointer entry from DRAM ($120\text{ cycles} / 37.5\text{ ns}$).
3. **DRAM Read 3 (PD Lookup)**: The IOMMU reads the Level 2 Page Directory entry from DRAM ($120\text{ cycles} / 37.5\text{ ns}$).
4. **DRAM Read 4 (PT Lookup)**: The IOMMU reads the Level 1 Page Table entry from DRAM ($120\text{ cycles} / 37.5\text{ ns}$).
5. **DRAM Write (Actual Payload Write)**: The IOMMU finally translates the address and writes the $64\text{-byte}$ DMA payload to DRAM ($120\text{ cycles} / 37.5\text{ ns}$).

Look at the physical disaster that occurred:
* To write **ONE single 64-byte DMA packet payload** to DRAM, the IOMMU was forced to execute **FOUR preliminary DRAM read accesses** just to translate the physical address!
* Total memory transfer latency exploded from $37.5\text{ nanoseconds}$ up to **$187.5\text{ nanoseconds}$** ($5\times$ latency penalty!).
* Over **$80\%$ of the system's external DRAM memory bus bandwidth** is completely consumed reading page table lookup trees, rather than transporting useful application data!

If an NVMe storage array or $100\text{-GbE}$ network card attempts to stream $20\text{ million packets per second}$ under this un-accelerated architecture, off-chip DRAM memory channels become completely saturated with page table lookup traffic, bringing the entire computer system to a grinding halt.

How do we design an IOMMU hardware architecture that remembers past $\text{IOVA} \to \text{PA}$ address translations, delivering physical addresses to peripheral DMA transactions in **$1\text{ single clock cycle}$** ($0.3125\text{ ns}$) and bypassing the 4-level DRAM page walk for $99\%+$ of incoming I/O packets?

To eliminate page walk memory latency penalties and accelerate peripheral data streaming, computer architectures employ the **I/O Translation Lookaside Buffer (IOTLB)** and **Hardware IOTLB Invalidation Queues**.

## Primitive 1: Multi-Level IOMMU Page Table Walk Mechanics

Now that we possess a clear intuitive mental model of 4-volume dictionaries and pocket quick-reference cards, let us examine the formal, rigorous engineering mechanics of **Multi-Level IOMMU Page Table Walks**.

To support 64-bit systems while managing memory footprint efficiency, the IOMMU structures its address translation tables into a 4-level tree hierarchy in DRAM memory:
1. **Page Map Level 4 Table (`PML4`)**
2. **Page Directory Pointer Table (`PDPT`)**
3. **Page Directory Table (`PD`)**
4. **Page Table (`PT`)**

```text
64-BIT IOVA ADDRESS BITFIELD DECOMPOSITION

 Bit 63             Bit 48 Bit 47   Bit 39 Bit 38   Bit 30 Bit 29   Bit 21 Bit 20   Bit 12 Bit 11 Bit 0
 ┌────────────────────────┬───────────────┬───────────────┬───────────────┬───────────────┬───────────┐
 │ Sign Extension / Unused│ PML4 Index    │ PDPT Index    │ PD Index      │ PT Index      │ Offset    │
 │ (Must be 0x0000)       │ (9 Bits)      │ (9 Bits)      │ (9 Bits)      │ (9 Bits)      │ (12 Bits) │
 └────────────────────────┴───────────────┴───────────────┴───────────────┴───────────────┴───────────┘
```

---

### Step-by-Step Hardware Page Table Walk Algorithm

When an incoming DMA transaction arrives with a 64-bit IO Virtual Address ($\text{IOVA}$), the IOMMU parses the lowest 48 bits of the address into five distinct index fields:
* **`PML4 Index` (Bits $[47:39]$ — 9 Bits)**: Selects 1 of 512 entries in the PML4 table.
* **`PDPT Index` (Bits $[38:30]$ — 9 Bits)**: Selects 1 of 512 entries in the PDPT table.
* **`PD Index` (Bits $[29:21]$ — 9 Bits)**: Selects 1 of 512 entries in the PD table.
* **`PT Index` (Bits $[20:12]$ — 9 Bits)**: Selects 1 of 512 entries in the leaf Page Table.
* **`Page Offset` (Bits $[11:0]$ — 12 Bits)**: Specifies the exact byte offset ($0 \dots 4095$) within the target $4\text{-KB}$ physical page.

```text
4-LEVEL IOMMU PAGE TABLE WALK DATAPATH

 IOVA Address
 ┌──────────┬──────────┬──────────┬──────────┬─────────────┐
 │ PML4 (9b)│ PDPT (9b)│ PD (9b)  │ PT (9b)  │ Offset (12b)│
 └────┬─────┴────┬─────┴────┬─────┴────┬─────┴──────┬──────┘
      │          │          │          │            │
      ▼          │          │          │            │
 ┌──────────┐    │          │          │            │
 │ PML4 Tab ├───►│          │          │            │
 └──────────┘    ▼          │          │            │
              ┌──────────┐  │          │            │
              │ PDPT Tab ├─►│          │            │
              └──────────┘  ▼          │            │
                         ┌──────────┐  │            │
                         │ PD Table ├─►│            │
                         └──────────┘  ▼            │
                                    ┌──────────┐    │
                                    │ PT Table ├──┐ │
                                    └──────────┘  │ │
                                                  ▼ ▼
                                     [ Physical Base Address PA ]
```

#### The Hardware Page Walk Execution Steps:

1. **Step 1 (PML4 Lookup)**:
   The IOMMU extracts `PML4 Index` (bits $[47:39]$) and reads the 8-byte entry from DRAM at physical address:
   $$\text{PML4\_Entry\_Addr} = \text{PML4\_Root\_Base} + (\text{PML4\_Index} \times 8)$$
   The PML4 entry returns the physical base address of the `PDPT` table ($\text{PDPT\_Base}$).
2. **Step 2 (PDPT Lookup)**:
   The IOMMU extracts `PDPT Index` (bits $[38:30]$) and reads the 8-byte entry from DRAM at physical address:
   $$\text{PDPT\_Entry\_Addr} = \text{PDPT\_Base} + (\text{PDPT\_Index} \times 8)$$
   The PDPT entry returns the physical base address of the `PD` table ($\text{PD\_Base}$).
3. **Step 3 (PD Lookup)**:
   The IOMMU extracts `PD Index` (bits $[29:21]$) and reads the 8-byte entry from DRAM at physical address:
   $$\text{PD\_Entry\_Addr} = \text{PD\_Base} + (\text{PD\_Index} \times 8)$$
   The PD entry returns the physical base address of the leaf `PT` table ($\text{PT\_Base}$).
4. **Step 4 (PT Leaf Lookup)**:
   The IOMMU extracts `PT Index` (bits $[20:12]$) and reads the 8-byte Page Table Entry (PTE) from DRAM at physical address:
   $$\text{PTE\_Addr} = \text{PT\_Base} + (\text{PT\_Index} \times 8)$$
   The PTE returns the **Physical Frame Number ($\text{PFN}$)** of the target $4\text{-KB}$ DRAM page and verifies Read/Write permissions ($R/W$).
5. **Step 5 (Physical Address Construction)**:
   The IOMMU combines the Physical Frame Number ($\text{PFN}$) with the original $12\text{-bit}$ Page Offset:

$$\mathbf{\text{Physical Address (PA)} = (\text{PFN} \ll 12) \quad \mathbf{\mid} \quad \text{Page Offset [11:0]}}$$

---

### The Mathematical Cost of an Un-Accelerated Page Walk

Let $T_{\text{DRAM}}$ be the average access latency to read an 8-byte page table entry from off-chip DRAM ($T_{\text{DRAM}} \approx 120\text{ CPU clock cycles} / 37.5\text{ ns}$).

The total time required to perform a 4-level page table walk ($T_{\text{walk}}$) is:

$$\mathbf{T_{\text{walk}} = 4 \times T_{\text{DRAM}} = 4 \times 120 \text{ cycles} = 480 \text{ CPU Clock Cycles (150.0 ns)!}}$$

To perform a single DMA transfer, the un-accelerated IOMMU burns **$480\text{ clock cycles}$ ($150.0\text{ nanoseconds}$)** in page table lookup delay alone!

## Primitive 2: I/O Translation Lookaside Buffer (IOTLB) Architecture

To eliminate the $480\text{-cycle}$ page table walk delay, hardware architects incorporate a high-speed translation cache directly onto the IOMMU silicon die: **The I/O Translation Lookaside Buffer (IOTLB)**.

> **An I/O Translation Lookaside Buffer (IOTLB)** is a small, high-speed, fully associative or set-associative on-chip SRAM cache array inside the IOMMU that stores recently translated IO Virtual Page Numbers ($\text{IOVPN}$) alongside their corresponding Physical Frame Numbers ($\text{PFN}$) and access permissions, allowing the IOMMU to deliver translated physical addresses in **$1\text{ single clock cycle}$**.

```text
IOTLB HIGH-SPEED ON-CHIP SRAM CACHE ARRAY

 Incoming DMA Request: (Domain ID = 2, IOVA = 0x42000)
       │
       ▼
 ┌─────────────────────────────────────────────────────────────┐
 │ IOTLB ON-CHIP SRAM CACHE ARRAY (64 to 512 Slots)            │
 │ Entry 0: [ V=1 | Domain=2 | IOVPN=0x42 | PFN=0x9000 | R/W=1 ]│◄── HIT!
 │ Entry 1: [ V=1 | Domain=1 | IOVPN=0x10 | PFN=0x4000 | R/W=1 ]│
 └─────────────┬───────────────────────────────────────────────┘
               │
               ▼ Physical Frame Number (PFN = 0x9000) Returned in 1 Clock Cycle!
 Physical Address PA = (0x9000 << 12) | Offset = 0x0000_0009_0000
 (Bypasses 4-Level DRAM Page Table Walk Completely!)
```

---

### Internal Structure of an IOTLB Entry

Each entry inside an IOTLB cache array contains six hardware fields:

```text
BITWISE FIELD LAYOUT OF AN IOTLB CACHE ENTRY

 ┌──────────┬──────────────┬────────────────────────┬───────────────────────┬─────────┬──────────┐
 │ Valid    │ Domain ID    │ IO Virtual Page Number │ Physical Frame Number │ Perms   │ Page Size│
 │ Bit (V)  │ (DID: 16b)   │ (IOVPN: 36 Bits)       │ (PFN: 40 Bits)        │ (R/W:2b)│ (PS: 2b) │
 └──────────┴──────────────┴────────────────────────┴───────────────────────┴─────────┴──────────┘
```

1. **Valid Bit ($V$)**: $1 =$ Entry holds a valid active translation; $0 =$ Entry is empty/invalid.
2. **Domain ID ($\text{DID}$ — $16\text{ Bits}$)**: Identifies the protection domain (virtual machine or device container) owning this translation.
3. **IO Virtual Page Number ($\text{IOVPN}$ — $36\text{ Bits}$)**: Stores the high-order $36\text{ bits}$ ($\text{IOVA}[47:12]$) of the virtual page address.
4. **Physical Frame Number ($\text{PFN}$ — $40\text{ Bits}$)**: Stores the translated $40\text{-bit}$ physical DRAM page base address.
5. **Permissions Field ($R/W$ — $2\text{ Bits}$)**: Stores Read ($R$) and Write ($W$) access permission flags.
6. **Page Size Flag ($\text{PS}$ — $2\text{ Bits}$)**: Indicates whether the mapping represents a standard $4\text{-KB}$ page, a $2\text{-MB}$ Large Page, or a $1\text{-GB}$ Huge Page.

---

### The IOTLB Hit vs. Miss Decision Tree

When an incoming DMA transaction arrives carrying $\text{Domain ID} = D$ and $\text{IOVA} = A_{\text{iova}}$:

The IOMMU extracts the virtual page number $\text{IOVPN} = A_{\text{iova}}[47:12]$ and performs a parallel bitwise comparison across all IOTLB entries simultaneously:

$$\text{IOTLB Hit Condition } k \iff (V_k == 1) \quad \mathbf{\&} \quad (\text{DID}_k == D) \quad \mathbf{\&} \quad (\text{IOVPN}_k == \text{IOVPN})$$

```text
IOTLB HIT VS MISS DECISION TREE

 Incoming DMA Request (Domain D, IOVA)
                   │
         Parallel IOTLB Lookup
                   │
         ┌─────────┴─────────┐
         │ HIT               │ MISS
         ▼                   ▼
 Read PFN from IOTLB!   Execute 4-Level DRAM Page Walk (480 Cycles).
 Construct PA in 1 Cycle! Load translation into IOTLB array.
 (99.5% of all accesses) (0.5% of all accesses)
```

#### Outcome A: IOTLB Hit ($99.5\%$ of DMA Transactions)
* A matching entry $k$ is found in the on-chip IOTLB SRAM array.
* The IOMMU verifies that the requested access direction (Read vs. Write) matches the entry's $R/W$ permission bits.
* The Physical Frame Number ($\text{PFN}_k$) is retrieved from the IOTLB array in **$1\text{ single clock cycle}$ ($0.3125\text{ ns}$)**!
* The physical DRAM write or read is dispatched across the interconnect immediately!

#### Outcome B: IOTLB Miss ($0.5\%$ of DMA Transactions)
* No matching entry exists in the IOTLB cache.
* The IOMMU initiates a full **4-Level Page Table Walk** in DRAM, spending $480\text{ clock cycles}$ to fetch the PTE from memory.
* Once the PTE is fetched, the IOMMU **loads the new translation $(\text{DID}, \text{IOVPN}, \text{PFN}, R/W)$ into an open slot in the IOTLB cache**.
* Future DMA transactions targeting the same $4\text{-KB}$ page will result in $100\%$ IOTLB Hits!

## Hardware Invalidation Queues (IOTLB Invalidation Commands)

A critical microarchitectural challenge arises when the operating system kernel modifies or unmaps a page table entry in system DRAM memory (e.g., when a user buffer is freed or a virtual machine is shut down).

If the operating system updates a page table entry in DRAM, **the IOTLB cache inside the IOMMU still holds the OLD cached translation**!

If the IOMMU continues using the cached IOTLB entry, a peripheral device could write to a memory page that was already reassigned to another application (**Stale Translation Incoherence Hazard**)!

To prevent stale translation hazards, the operating system kernel and IOMMU execute the **Hardware Invalidation Queue Protocol**.

```text
HARDWARE INVALIDATION QUEUE ARCHITECTURE

 Host OS Kernel (Producer)                      IOMMU Hardware Engine (Consumer)
 ┌───────────────────────────┐                  ┌───────────────────────────┐
 │ Modifies PTE in DRAM      │                  │ Fetches Invalidation Cmds │
 ├───────────────────────────┤                  │ from Invalidation Queue   │
 │ Writes Invalidation Cmd   │                  ├───────────────────────────┤
 │ to Invalidation Queue(IQ) │                  │ Clears matching IOTLB     │
 ├───────────────────────────┤                  │ entries in 1 Clock Cycle! │
 │ Rings IQ MMIO Doorbell    ├─────────────────►│ Sets Valid Bit V_k <= 0   │
 └───────────────────────────┘                  └───────────────────────────┘
```

---

### The Three IOTLB Invalidation Commands

The operating system kernel posts three standardized **Invalidation Commands** to the IOMMU's Memory-Mapped Invalidation Queue (IQ):

#### 1. Page-Selective Invalidation (`IOTLB_INV_PAGE`)
* **Command Payload**: Domain ID ($D$) + Specific IO Virtual Page Number ($\text{IOVPN}$).
* **Hardware Action**: The IOMMU searches its IOTLB array and clears the Valid bit ($V_k \Leftarrow 0$) for the single matching entry $(\text{DID} == D \ \mathbf{\&} \ \text{IOVPN}_k == \text{IOVPN})$.

#### 2. Domain-Selective Invalidation (`IOTLB_INV_DOMAIN`)
* **Command Payload**: Domain ID ($D$).
* **Hardware Action**: The IOMMU clears the Valid bits ($V \Leftarrow 0$) for **ALL IOTLB entries belonging to Domain $D$** (e.g., when an entire Virtual Machine is shut down).

#### 3. Global Invalidation (`IOTLB_INV_GLOBAL`)
* **Command Payload**: Global Flush Command.
* **Hardware Action**: The IOMMU clears the Valid bits ($V \Leftarrow 0$) for **EVERY entry in the entire IOTLB array** (e.g., during major operating system kernel re-configurations).

---

### The Invalidation Queue Handshake Sequence

1. **Software Page Modification**: The OS kernel updates a Page Table Entry in system DRAM.
2. **Command Posting**: The OS writes an `IOTLB_INV_PAGE` command into the IOMMU Invalidation Queue in system RAM.
3. **Doorbell Ringing**: The OS writes to the IOMMU's **Invalidation Queue Tail Doorbell Register** (`IQ_Tail`).
4. **Hardware Execution**: The IOMMU fetches the invalidation command from RAM and invalidates the specified IOTLB entry in **$1\text{ clock cycle}$**.
5. **Completion Synchronization**: The IOMMU executes an Invalidation Wait Command (`IQ_WAIT`), informing the OS kernel that the stale translation has been erased from all hardware caches across the chip!

## Mathematical Performance Model: Accelerated vs. Un-Accelerated Translation

To quantify the performance impact of IOTLB translation caches, let us derive a mathematical model for average memory translation latency ($T_{\text{avg}}$) as a function of the **IOTLB Hit Ratio ($H$)**.

Let:
* $H$ be the IOTLB cache hit ratio ($0.0 \le H \le 1.0$, typically $H \approx 0.995$ or $99.5\%$).
* $M = (1.0 - H)$ be the IOTLB miss ratio ($M \approx 0.005$ or $0.5\%$).
* $T_{\text{hit}}$ be the IOTLB hit latency ($T_{\text{hit}} = 1\text{ CPU clock cycle}$).
* $T_{\text{walk}}$ be the full 4-level page table walk delay ($T_{\text{walk}} = 480\text{ CPU clock cycles}$).

The average memory translation latency ($T_{\text{avg}}$) in clock cycles is:

$$\mathbf{T_{\text{avg}} = (H \cdot T_{\text{hit}}) + ((1.0 - H) \cdot (T_{\text{hit}} + T_{\text{walk}}))}$$

Simplifying:

$$T_{\text{avg}} = T_{\text{hit}} + ((1.0 - H) \cdot T_{\text{walk}})$$

```text
AVERAGE IOMMU TRANSLATION LATENCY VS. IOTLB HIT RATIO

 Average Latency (Cycles)
  480 ┼ * Un-Accelerated Page Walk (0% Hit Ratio = 480 Cycles!)
      │  \
  300 ┼   \
      │    \
  100 ┼     \
    3.4 ┴────*──────────────────────────────────────────► IOTLB Hit Ratio (H)
            99.5% Hit Ratio = 3.4 Cycles! (141x Faster!)
```

Let us evaluate $T_{\text{avg}}$ for an IOTLB with a $99.5\%$ hit ratio ($H = 0.995$):

$$T_{\text{avg}} = 1 + ((1.0 - 0.995) \cdot 480) = 1 + (0.005 \cdot 480) = 1 + 2.4 = \mathbf{3.40 \text{ CPU Clock Cycles!}}$$

$$\text{Translation Speedup Factor} = \frac{T_{\text{walk}}}{T_{\text{avg}}} = \frac{480.0\text{ cycles}}{3.40\text{ cycles}} \approx \mathbf{141.18\times \text{ Performance Speedup!}}$$

#### Physical Hardware Result:
By maintaining a $99.5\%$ IOTLB hit ratio, the IOTLB translation cache reduces average address translation delay from $480\text{ clock cycles}$ down to **$3.4\text{ clock cycles}$ ($141.18\times$ faster!)**, eliminating interconnect backpressure and allowing peripheral devices to stream DMA data at full multi-gigabit wire speed!

### Scenario and Parameters

You are a senior memory interconnect architect auditing the IOMMU performance of a $3.2\text{ GHz}$ 64-bit server processor ($T_{\text{clk}} = 0.3125\text{ ns} = 312.5\text{ ps}$).

The server is equipped with a $100\text{-Gigabit}$ Ethernet NIC Endpoint streaming incoming network packets into DRAM memory at a rate of **$100,000\text{ packets per second}$**.

Each network packet is **$64\text{ Kilobytes}$ ($65,536\text{ bytes}$)** in size, spanning **$1,024$ 64-byte cache lines**.

```text
3.2 GHz SERVER PROCESSOR WITH 100-GBE NIC AND IOMMU IOTLB CACHE

 100-GbE NIC Endpoint ──► [ IOMMU IOTLB Cache (99.5% Hit Ratio) ] ──► System DRAM
 100k Packets / Sec       4-Level Page Walk = 480 Cycles              Latency = 120 Cycles
```

#### Hardware & IOMMU Parameters:
* CPU Clock Frequency: $f_{\text{clk}} = 3.2\text{ GHz}$ ($T_{\text{clk}} = 0.3125\text{ ns}$).
* Main DRAM Memory Read Latency: $T_{\text{DRAM}} = 120\text{ CPU clock cycles}$ ($37.5\text{ ns}$).
* 4-Level IOMMU Page Table Walk Delay: $T_{\text{walk}} = 4 \times 120 = \mathbf{480 \text{ CPU Clock Cycles}}$ ($150.0\text{ ns}$).
* On-Chip IOTLB Hit Latency: $T_{\text{hit}} = \mathbf{1 \text{ CPU Clock Cycle}}$ ($0.3125\text{ ns}$).
* IOTLB Cache Hit Ratio: $H = 99.5\%$ ($0.5\%$ miss rate).

#### Candidate IOMMU System Architectures to Compare:
* **System 0 (Un-Accelerated IOMMU — No IOTLB)**: Every DMA transaction executes a full 4-level page table walk in DRAM ($T_{\text{walk}} = 480\text{ cycles}$).
* **System 1 (Accelerated IOMMU — $99.5\%$ IOTLB Hit Ratio)**: $99.5\%$ of transactions hit in the on-chip IOTLB ($1\text{ cycle}$); $0.5\%$ miss and execute a page table walk ($481\text{ cycles}$).

#### Your Objective

1. Calculate the average address translation latency per $64\text{-byte}$ DMA line (in clock cycles and nanoseconds) for System 0 vs System 1.
2. For a single $64\text{-KB}$ packet ($1,024\text{ lines}$), calculate total address translation delay $T_{\text{trans\_packet}}$ (in clock cycles and microseconds) for System 0 vs System 1.
3. Calculate the total off-chip DRAM memory bandwidth consumed **purely reading page table trees** (in MB/sec and GB/sec) for System 0 vs System 1 across $100,000\text{ packets per second}$.
4. Calculate the percentage reduction in page table translation latency and the overall **Performance Speedup Factor** of System 1 (IOTLB) over System 0.
5. Trace an **`IOTLB_INV_PAGE` Invalidation Command** executed by the OS kernel when unmapping an IOVA page, showing the bitwise state changes in the IOTLB array.
6. Verify mathematical, structural, and timing correctness.

### Step-by-Step Derivation

#### Step 1: Calculate Average Address Translation Latency per Line

Each $64\text{-byte}$ DMA line requires one address translation.

##### 1. System 0 (Un-Accelerated IOMMU — No IOTLB):
Every line requires a 4-level DRAM page walk ($4 \times 120\text{ cycles}$):

$$T_{\text{line,0}} = T_{\text{walk}} = \mathbf{480.0 \text{ CPU Clock Cycles}}$$

$$T_{\text{line,0\_time}} = 480.0 \times 0.3125 \times 10^{-9}\text{ s} = \mathbf{150.00 \text{ nanoseconds}} \quad (0.150\ \mu\text{s})$$

##### 2. System 1 (Accelerated IOMMU — $99.5\%$ IOTLB Hit Ratio):
We apply the average translation latency formula ($H = 0.995$):

$$T_{\text{line,1}} = T_{\text{hit}} + ((1.0 - H) \cdot T_{\text{walk}}) = 1 + ((0.005) \cdot 480) = 1 + 2.40 = \mathbf{3.40 \text{ CPU Clock Cycles}}$$

$$T_{\text{line,1\_time}} = 3.40 \times 0.3125 \times 10^{-9}\text{ s} = \mathbf{1.0625 \text{ nanoseconds}}$$

##### Translation Latency Reduction Result:
$$\text{Latency Saved per Line} = 150.00\text{ ns} - 1.0625\text{ ns} = \mathbf{148.9375 \text{ nanoseconds saved per line!}}$$

The IOTLB reduced average address translation latency from $150.00\text{ ns}$ down to **$1.0625\text{ ns}$ ($99.29\%$ latency reduction)**!

---

#### Step 2: Calculate Translation Delay per $64\text{-KB}$ Packet ($1,024\text{ Lines}$)

Each $64\text{-KB}$ packet contains $1,024\text{ lines}$ ($64\text{ bytes}$ per line).

##### 1. System 0 Translation Delay per Packet ($T_{\text{trans\_packet,0}}$):

$$T_{\text{trans\_packet,0}} = 1,024 \text{ lines} \times 480 \text{ cycles/line} = \mathbf{491,520 \text{ CPU Clock Cycles}}$$

$$T_{\text{trans\_packet,0\_time}} = 491,520 \times 0.3125 \times 10^{-9}\text{ s} = \mathbf{153.60 \text{ microseconds}} \quad (153,600\text{ ns})$$

##### 2. System 1 Translation Delay per Packet ($T_{\text{trans\_packet,1}}$):

$$T_{\text{trans\_packet,1}} = 1,024 \text{ lines} \times 3.40 \text{ cycles/line} = \mathbf{3,481.60 \text{ CPU Clock Cycles}}$$

$$T_{\text{trans\_packet,1\_time}} = 3,481.60 \times 0.3125 \times 10^{-9}\text{ s} = \mathbf{1.088 \text{ microseconds}} \quad (1,088\text{ ns})$$

```text
PACKET TRANSLATION TIME COMPARISON (1,024 LINES)

 System 0 (No IOTLB) : 491,520 Cycles (153.60 us) ──► 153.60 microseconds!
 System 1 (With IOTLB): 3,481.6 Cycles (1.088 us)  ──► 1.088 microseconds! (141.2x FASTER!)
```

#### Step 3: Calculate DRAM Memory Bandwidth Consumed by Page Table Walks

Each page table entry read fetches an $8\text{-byte}$ PTE from DRAM. A 4-level page table walk fetches 4 8-byte entries $= 32\text{ bytes}$ of page table data per miss.

Workload rate $= 100,000\text{ packets per second} \times 1,024\text{ lines/packet} = \mathbf{102,400,000 \text{ DMA lines/second}}$.

##### 1. System 0 Page Walk DRAM Bandwidth ($\text{BW}_{\text{PT,0}}$):
System 0 misses on $100\%$ of lines ($102,400,000\text{ page walks/sec}$):

$$\text{BW}_{\text{PT,0}} = 102,400,000 \text{ walks/sec} \times 32 \text{ Bytes/walk} = 3,276,800,000 \text{ Bytes/sec}$$

$$\mathbf{\text{BW}_{\text{PT,0}} = 3,276.80 \text{ MB/sec} = 3.2768 \text{ GB/sec}}$$

Under System 0, **$3.2768\text{ Gigabytes per second}$** of off-chip DRAM bandwidth is consumed *purely reading page table trees*!

##### 2. System 1 Page Walk DRAM Bandwidth ($\text{BW}_{\text{PT,1}}$):
System 1 misses on $0.5\%$ of lines ($0.005 \times 102,400,000 = 512,000\text{ page walks/sec}$):

$$\text{BW}_{\text{PT,1}} = 512,000 \text{ walks/sec} \times 32 \text{ Bytes/walk} = 16,384,000 \text{ Bytes/sec}$$

$$\mathbf{\text{BW}_{\text{PT,1}} = 16.384 \text{ MB/sec} = 0.016384 \text{ GB/sec}}$$

##### DRAM Bandwidth Savings Result:
$$\text{DRAM Bandwidth Saved} = 3.2768\text{ GB/s} - 0.016384\text{ GB/s} = \mathbf{3.2604 \text{ GB/sec Saved!}}$$

The IOTLB eliminated **$3.2604\text{ Gigabytes per second}$ of wasted DRAM bus traffic**, saving memory power and leaving DRAM channels open for CPU applications!

#### Step 4: Calculate Performance Speedup Factor

Let us calculate the performance speedup factor of System 1 (IOTLB) over System 0 (Un-Accelerated Page Walk):

$$\text{Speedup} = \frac{T_{\text{trans\_packet,0}}}{T_{\text{trans\_packet,1}}} = \frac{153.60\ \mu\text{s}}{1.088\ \mu\text{s}} = \frac{491,520\text{ cycles}}{3,481.6\text{ cycles}} \approx \mathbf{141.176\times \text{ Performance Speedup!}}$$

#### Step 5: Trace IOTLB Invalidation Command Execution

When the operating system kernel unmaps IOVA page `0x40000` (Domain 3), it issues an `IOTLB_INV_PAGE` command:

1. **OS Command Posting**: The OS writes an 8-byte invalidation descriptor to the IOMMU Invalidation Queue in RAM:
   * `Opcode = 0x01` (`IOTLB_INV_PAGE`)
   * `Domain ID = 3`
   * `Target IOVPN = 0x000000040` (Virtual Page `0x40000`)
2. **Doorbell Ringing**: The OS writes `IQ_Tail` MMIO register.
3. **Hardware Invalidation**: The IOMMU fetches the command and checks its IOTLB array slots:
   * Slot 0: `Valid = 1`, `Domain = 3`, `IOVPN = 0x000000040` $\implies$ **MATCH FOUND!**
   * The IOMMU clears Slot 0's Valid bit: **$V_0 \Leftarrow 0$** in $1\text{ clock cycle}$!
4. **Result**: The stale translation is erased from hardware. The next DMA access targeting `0x40000` triggers a fresh page walk or fault check with $100\%$ security!

1. **Page Walk Latency Verification**:
   * $4\text{ levels} \times 120\text{ cycles/level} = 480\text{ cycles}$.

   * $T_{\text{avg}} = 1 + (0.005 \times 480) = 1 + 2.4 = 3.4\text{ cycles}$.

All 4-level page table walk equations, IOTLB $99.5\%$ hit ratio speedup models, page offset decompositions, invalidation queue state steps, and DRAM bandwidth conservation metrics evaluate with 100% mathematical, physical, and logical precision.

## Key Output Primitives

This lesson formally delivers the following conceptual primitives to your digital logic engineering toolbox:

* **IOMMU Page Table Walk**: The hardware translation process where the IOMMU traverses a multi-level page table tree (`PML4` $\to$ `PDPT` $\to$ `PD` $\to$ `PT`) in main DRAM memory to resolve an IO Virtual Address ($\text{IOVA}$) into a physical DRAM address ($\text{PA}$), incurring a $4\times$ to $5\times$ memory access latency penalty when un-cached.
* **IOTLB Translation Cache**: An on-chip SRAM cache array inside the IOMMU that stores recently resolved $\text{IOVPN} \to \text{PFN}$ translations and permissions, delivering translated physical addresses in $1\text{ single clock cycle}$ ($141\times$ latency reduction) and utilizing hardware Invalidation Queues (`IOTLB_INV`) to clear stale entries when page tables are modified by the operating system.
