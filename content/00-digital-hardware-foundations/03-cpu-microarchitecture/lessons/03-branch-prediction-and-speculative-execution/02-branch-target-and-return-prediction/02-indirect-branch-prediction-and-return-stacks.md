# Indirect Branch Target Prediction and Return Stack Buffer Hardware

## The Polymorphic Jump Crisis: When One Instruction Has Multiple Targets

Imagine a 5-stage pipelined processor core executing a complex object-oriented C++ application or a software virtual machine interpreter. The program contains a polymorphic virtual method call executed inside a high-speed processing loop:

```cpp
// POLYMORPHIC VIRTUAL METHOD CALL
shape_ptr->draw(); // Compiles to an indirect register jump: JALR x1, 0(x5)
```

Look at the assembly instruction generated by this C++ method call: `JALR x1, 0(x5)` (Jump and Link Register). 

Unlike a standard conditional branch instruction whose jump destination is hardcoded as a fixed offset relative to the Program Counter ($PC + \text{offset}$), an **Indirect Branch Instruction** reads its target jump address dynamically out of a CPU register ($x5$).

Now, trace what happens as the program executes this exact same `JALR x1, 0(x5)` instruction located at memory address `0x0000_0100` across three consecutive iterations of the software loop:

1. **Iteration 1**: `shape_ptr` points to a **Circle** object. Register $x5$ holds address `0x0000_1000` (the start of `Circle::draw()`). The instruction jumps to `0x0000_1000`.
2. **Iteration 2**: `shape_ptr` points to a **Square** object. Register $x5$ holds address `0x0000_2000` (the start of `Square::draw()`). The instruction jumps to `0x0000_2000`.
3. **Iteration 3**: `shape_ptr` points to a **Triangle** object. Register $x5$ holds address `0x0000_3000` (the start of `Triangle::draw()`). The instruction jumps to `0x0000_3000`.

```text
THE MULTI-TARGET INDIRECT JUMP CRISIS

 Instruction Address 0x0000_0100 : JALR x1, 0(x5)
                                    │
       ┌────────────────────────────┼────────────────────────────┐
       ▼                            ▼                            ▼
 Iteration 1 Target          Iteration 2 Target          Iteration 3 Target
 0x0000_1000 (Circle)        0x0000_2000 (Square)        0x0000_3000 (Triangle)
```

Now, look at the physical impossibility facing a standard **Branch Target Buffer (BTB)**:

A standard BTB is a simple cache that maps **ONE instruction address ($PC$) to ONE target address ($PC_{\text{target}}$)**. 
* On Iteration 1, the BTB records: `0x0000_0100 -> 0x0000_1000`.
* On Iteration 2, the processor fetches `0x0000_0100`. The standard BTB reads its cache entry and predicts target `0x0000_1000` (Circle). But the program wants to jump to `0x0000_2000` (Square)!
* The standard BTB **MISPREDICTS THE TARGET ADDRESS!**

Every single time the object type changes in software, a standard BTB fails, triggering a 2-cycle pipeline flush!

A similar, equally destructive target misprediction crisis occurs on **Function Return Instructions** (`RET` / `JALR x0, x1, 0`):

Suppose a utility function `compute_hash()` is called from three different places in code: Location A (`0x0004_0000`), Location B (`0x0008_0000`), and Location C (`0x000C_0000`).

When `compute_hash()` finishes, its final `RET` instruction located at address `0x0000_0500` must return to Location A, B, or C depending on **who called it**!

A standard BTB remembers only the *last* location that called the function. Every time `compute_hash()` is called from a different location, the standard BTB mispredicts the return address, causing constant pipeline flushes!

```text
FUNCTION RETURN TARGET DIVERSITY

 Call Location A (0x0004_0000) ──┐
 Call Location B (0x0008_0000) ──┼──► [ Function compute_hash() ] ──► RET Inst at 0x0000_0500
 Call Location C (0x000C_0000) ──┘                                   (Which caller to return to?!)
```

Standard Branch Target Buffers are completely blind to dynamic target diversity.

To predict dynamic multi-target indirect jumps and nested function returns with near $100\%$ accuracy, microarchitects developed two specialized hardware predictors: **The Indirect Branch Target Buffer (iBTB)** and **The Return Stack Buffer (RSB / RAS)**.

## Primitive 1: Indirect Branch Target Buffer (iBTB) Architecture

Now that we understand why polymorphic jumps require path context, let us examine the formal hardware architecture of an **Indirect Branch Target Buffer (iBTB)**.

An iBTB is a specialized target address cache designed to predict multi-target indirect jumps (`JALR`).

Unlike a standard BTB—which indexes its memory array using *only* the instruction address ($PC[k+1:2]$)—an iBTB indexes its array using a **bitwise Exclusive-OR (XOR) hash between the instruction address ($PC$) and the Global History Register ($GHR$)**:

```text
INDIRECT BTB (iBTB) XOR HASH INDEXING SCHEMATIC

 Program Counter Address (PC_IF[k+1:2]) ──►[ k-Bit XOR Gate Array ]──► k-Bit iBTB Index
 Global History Register (GHR[m-1:0])  ──►[   (Bitwise XOR)   ]     (Selects 1 of 2^k Entries)
                                                                             │
                                                                             ▼
                                                       Indirect Branch Target Buffer (iBTB)
                                                       ┌──────────────────────────────────┐
                                                       │ Valid │ Tag (PC) │ Target PC     │
                                                       └──────────────────┴───────┬────────┘
                                                                                  │
                                                                                  ▼
                                                                      iBTB_Target_PC [31:0]
```

---

### The iBTB Indexing Formula

To calculate the $k$-bit memory index for the iBTB array, the hardware evaluates:

$$
\text{iBTB\_Index} = PC_{\text{IF}}[k+1 : 2] \quad \oplus \quad \left\{ \text{Zero\_Padding}, \, GHR[m-1 : 0] \right\}
$$

Where:
* $\text{iBTB\_Index}$ is the $k$-bit address used to read the iBTB SRAM array.
* $PC_{\text{IF}}[k+1 : 2]$ is the lower instruction address bits from the IF stage.
* $GHR[m-1 : 0]$ is the $m$-bit Global History Register tracking recent branch paths.
* $\oplus$ represents the bitwise Exclusive-OR (XOR) operation.

---

### How Path Context Resolves Polymorphic Jump Targets

Let us trace how the iBTB handles the virtual method call `shape_ptr->draw()` located at address `0x0000_0100` ($PC[8:2] = \text{7'd64}$):

1. **Scenario A (Drawing a Circle)**:
   * The program executed path A before calling `draw()`. The $GHR$ holds history pattern `8'b0000_0001`.
   * $\text{iBTB\_Index}_A = 64_{10} \oplus 1_{10} = \mathbf{65_{10}} \quad (\text{Entry } 65)$.
   * Entry 65 in the iBTB stores Target `0x0000_1000` (`Circle::draw()`).
   * The iBTB outputs Target `0x0000_1000`! **CORRECT PREDICTION!**
2. **Scenario B (Drawing a Square)**:
   * The program executed path B before calling `draw()`. The $GHR$ holds history pattern `8'b0000_0010`.
   * $\text{iBTB\_Index}_B = 64_{10} \oplus 2_{10} = \mathbf{66_{10}} \quad (\text{Entry } 66)$.
   * Entry 66 in the iBTB stores Target `0x0000_2000` (`Square::draw()`).
   * The iBTB outputs Target `0x0000_2000`! **CORRECT PREDICTION!**

```text
iBTB POLYMORPHIC TARGET RESOLUTION

 Same Instruction Address (PC = 0x0000_0100 / Base Index 64)
  ├── With Circle Path History (GHR = 1) ──► XOR Index 65 ──► Target 0x0000_1000 (Circle!)
  └── With Square Path History (GHR = 2) ──► XOR Index 66 ──► Target 0x0000_2000 (Square!)
```

Look at the microarchitectural triumph!
* The exact same instruction address (`0x0000_0100`) was routed to **two completely different target entries** in the iBTB array (Entry 65 vs Entry 66) based on the preceding path history!
* Polymorphic method calls and switch jump tables are predicted with near $100\%$ accuracy, eliminating target misprediction flushes!

## Primitive 2: Return Stack Buffer (RSB / RAS) LIFO Call/Return Prediction

While the iBTB excels at general multi-target register jumps, function call and return operations (`CALL` / `RET`) exhibit a strict mathematical structure that allows an even faster, $100\%$ accurate hardware predictor: **The Return Stack Buffer (RSB)** (also known as the **Return Address Stack - RAS**).

In software execution, function calls and returns follow a strict **Last-In, First-Out (LIFO)** nested call structure:

```text
NESTED FUNCTION CALL STACK FLOW

 Main Program ──► CALL foo() ──► Function foo() ──► CALL bar() ──► Function bar()
                  (Push Ret A)                    (Push Ret B)     (Executes...)
                                                                         │
 Main Program ◄── RET (Pop Ret A) ◄── Function foo() ◄── RET (Pop Ret B) ◄┘
```

When function `main()` calls `foo()`, `foo()` calls `bar()`. When `bar()` finishes, it returns to `foo()`. When `foo()` finishes, it returns to `main()`.

---

### Hardware Architecture of the Return Stack Buffer

A **Return Stack Buffer (RSB)** is a small, dedicated hardware LIFO memory stack (typically 8 to 16 entries deep) located directly inside the Instruction Fetch (IF) or Instruction Decode (ID) stage.

It is managed by a circular **Top-of-Stack Pointer ($\text{TOS}$)**:

```text
RETURN STACK BUFFER (RSB) HARDWARE LIFO STRUCTURE

 Top-of-Stack Pointer (TOS = 2)
                 │
                 ▼
 ┌──────────────────────────────────────────────┐
 │ RSB Entry 3 : 32'h0000_0000                  │
 │ RSB Entry 2 : 32'h0000_2004  ◄── TOP OF STACK│ (Most Recent Return Address!)
 │ RSB Entry 1 : 32'h0000_1004                  │
 │ RSB Entry 0 : 32'h0000_0014                  │ (Oldest Return Address)
 └──────────────────────────────────────────────┘
```

The RSB operates on two simple hardware commands triggered during instruction decoding or pre-decoding:

#### 1. The RSB PUSH Operation (Executed on Function Call Instructions: `JAL` / `JALR rd != x0`)
When the Instruction Fetch or Decode stage detects a function call instruction (an instruction that jumps to a sub-routine and saves a link address into register $rd$, such as `JAL x1, target`):

1. The hardware calculates the sequential return address where the sub-routine MUST eventually return:
   $$\text{Return\_PC} = PC_{\text{call}} + 4$$
2. The hardware increments the Top-of-Stack pointer: $\text{TOS} \Leftarrow (\text{TOS} + 1) \pmod N$.
3. The hardware **PUSHES** $\text{Return\_PC}$ onto the top of the stack:
   $$\text{RSB}[\text{TOS}] \Leftarrow PC_{\text{call}} + 4$$

```text
RSB PUSH OPERATION (FUNCTION CALL DETECTED)

 Function Call Instruction at PC = 0x0000_1000 (JAL x1, target)
  1. Calculate Return Address : PC + 4 = 0x0000_1004
  2. Increment Stack Pointer  : TOS <= TOS + 1
  3. Push onto RSB Array      : RSB[TOS] <= 0x0000_1004
```

---

#### 2. The RSB POP Operation (Executed on Function Return Instructions: `RET` / `JALR x0, x1, 0`)
When the Instruction Fetch stage detects a function return instruction (an instruction that jumps to the address stored in link register $x1$ without saving a new link address, such as `RET`):

1. The hardware reads the predicted return address directly from the top of the RSB stack:
   $$\text{Predict\_Return\_PC} = \text{RSB}[\text{TOS}]$$
2. The hardware decrements the Top-of-Stack pointer: $\text{TOS} \Leftarrow (\text{TOS} - 1) \pmod N$.
3. The Next-PC multiplexer in the IF stage immediately loads $PC_{\text{next}} \Leftarrow \text{Predict\_Return\_PC}$.

```text
RSB POP OPERATION (FUNCTION RETURN DETECTED)

 Function Return Instruction at PC = 0x0000_2500 (RET)
  1. Read Top-of-Stack Address : Predict_PC = RSB[TOS] (0x0000_1004)
  2. Decrement Stack Pointer   : TOS <= TOS - 1
  3. Override Program Counter  : PC <= 0x0000_1004 (ZERO-CYCLE BRANCH PENALTY!)
```

Look at the extraordinary microarchitectural perfection of the RSB!
* The function return instruction (`RET`) did NOT use the standard BTB.
* It did NOT run a weather forecast. It did NOT search a memory table.
* **It popped the exact, 100% true return address directly off its internal LIFO stack!**
* The function return jumps to the exact caller address on the very next clock cycle with **ZERO CLOCK CYCLES OF BRANCH PENALTY!**

## Speculative RSB Pointer Management & Circular Buffer Recovery

While the Return Stack Buffer provides near $100\%$ return accuracy, physical pipelined hardware introduces a critical operational challenge: **Speculative Execution Corruption**.

In a 5-stage pipeline, function calls and returns are detected in the Instruction Fetch (IF) or Instruction Decode (ID) stage. 

What happens if the processor speculatively fetches a function call or return instruction down a branch path that turns out to be **WRONG** (a branch misprediction occurring in the EX stage)?

```text
SPECULATIVE RSB STACK CORRUPTION SCENARIO

 Cycle 1 (IF)  : Branch Instruction BEQ predicts TAKEN (Speculative Path!).
 Cycle 2 (IF)  : Speculative Path contains a Function Call (JAL)!
                 RSB executes PUSH! (TOS <= TOS + 1). (RSB POINTER CORRUPTED!)
 Cycle 3 (EX)  : BEQ evaluates NOT-TAKEN! (MISPREDICTION DETECTED!)
                 Pipeline Flushed!
                 BUT THE RSB STACK POINTER WAS ALREADY ALTERED!
```

Look at the corruption! 
An instruction sitting on an invalid speculative branch path altered the RSB stack pointer ($\text{TOS}$). When the speculative path is flushed, if the RSB pointer is not restored, **all subsequent function returns in the real program will pop the wrong return address**, crashing the application!

---

### The Solution: Dual-Pointer RSB Checkpointing

To protect the RSB from speculative corruption, modern processor cores maintain two separate Top-of-Stack pointers:

1. **Speculative Top-of-Stack Pointer ($\text{TOS}_{\text{spec}}$)**:
   Used in the Instruction Fetch (IF) stage to push and pop return addresses speculatively during high-speed fetching.
2. **Committed Top-of-Stack Pointer ($\text{TOS}_{\text{commit}}$)**:
   Updated ONLY when a function call or return instruction reaches the Writeback (WB) stage and officially commits to architectural state.

```text
DUAL-POINTER RSB CHECKPOINT RECOVERY

 IF Stage (Speculative)  ──► Uses TOS_spec for high-speed PUSH/POP
                             │
                             ▼ (Branch Misprediction Detected in EX Stage!)
 Recovery Action         ──► Restore TOS_spec <= TOS_commit!
                             (Speculative stack pointer instantly repaired!)
```

When a branch misprediction or exception flush occurs in the EX stage:
1. The pipeline flushes the speculative instructions.
2. The hardware **instantly restores the speculative pointer from the committed pointer**:
   $$\text{TOS}_{\text{spec}} \Leftarrow \text{TOS}_{\text{commit}}$$
3. The RSB stack pointer is repaired in zero clock cycles, ready to resume correct execution!

---

### Handling Deep Function Call Overflows

What happens if a program uses deep recursion or nested function calls that exceed the physical capacity of the RSB (e.g., 20 nested calls on a 16-entry RSB)?

The RSB is implemented as a **Circular Array Buffer**:
* When the 17th function call arrives, the pointer wraps around ($\text{TOS} = (15 + 1) \pmod{16} = 0$) and overwrites the oldest return address at entry 0.
* When the program eventually returns back up the call chain:
  * The top 16 return instructions **HIT in the RSB** with $100\%$ accuracy!
  * Only the 17th return instruction misses in the RSB (since its entry was overwritten). It falls back to a standard 1-cycle ID-stage target calculation!

```text
CIRCULAR BUFFER RSB OVERFLOW BEHAVIOR (16 ENTRIES)

 Calls 1 to 16  : PUSH entries 0 to 15 cleanly.
 Call 17        : Overwrites Entry 0 (Oldest call).
 Returns 17..2  : 16 consecutive RSB HITS! (0-cycle penalty).
 Return 1       : RSB Miss (Falls back to standard target adder).
```

Even under deep recursion, an RSB delivers $95\%+$ overall prediction accuracy across the entire program.

## Complete Integrated Branch Prediction Architecture

In a production-grade microprocessor core, all four branch prediction primitives operate together in a unified, multi-tier prediction hierarchy inside the Instruction Fetch (IF) stage:

```text
UNIFIED MULTI-TIER IF-STAGE BRANCH PREDICTION HIERARCHY

 Instruction Address PC_IF[31:0]
  │
  ├─►[ 1. Gshare Predictor ]─────────────► Predicts Direction (Taken / Not-Taken)
  │
  ├─►[ 2. Return Stack Buffer (RSB) ]────► Predicts Return Target (if RET)
  │
  ├─►[ 3. Indirect BTB (iBTB) ]──────────► Predicts Dynamic Target (if JALR)
  │
  └─►[ 4. Standard Tagged BTB ]──────────► Predicts Static Target (if JAL/BEQ)
                                                 │
                                                 ▼
                                        Next-PC MUX Selects Target!
```

### The IF-Stage Target Selection Priority:
On every clock cycle, when $PC_{\text{IF}}$ enters the Instruction Fetch stage:

1. **If Instruction is a Return (`RET`)**:
   Select target from **Return Stack Buffer ($\text{RSB}[\text{TOS}]$)**.
2. **If Instruction is an Indirect Jump (`JALR`)**:
   Select target from **Indirect BTB ($\text{iBTB\_Target}$)**.
3. **If Instruction is a Direct Branch/Jump (`BEQ`/`JAL`)**:
   Select target from **Standard BTB ($\text{BTB\_Target}$)**.
4. **Default Sequential Fallback**:
   Select $PC_{\text{IF}} + 4$.

```text
PREDICTION HIERARCHY SELECTION MATRIX

 Instruction Type │ Primary Direction Source │ Primary Target Source │ Typical Accuracy
──────────────────┼──────────────────────────┼───────────────────────┼──────────────────
 Conditional Loop │ Gshare Predictor (XOR)   │ Standard Tagged BTB   │ 96% Accuracy
 Indirect Jump    │ Gshare Predictor         │ Indirect BTB (iBTB)   │ 94% Accuracy
 Function Return  │ Always-Taken (Implicit)  │ Return Stack (RSB)    │ 99% Accuracy!
```

This multi-tier prediction hierarchy eliminates $98\%$ of all branch penalty flushes in high-performance processors!

### Step-by-Step Derivation

#### Step 1: Calculate Target Prediction Path Delay and Timing Slack

Let us trace the physical critical path through the target selection network in the IF stage:

1. iBTB XOR Hash & Memory Array Read: $t_{\text{ibtb\_read}} = 0.38\text{ ns}$.
2. iBTB Tag Match Comparator: $t_{\text{tag\_comp}} = 0.12\text{ ns}$.
3. Target Selection MUX (RSB vs iBTB vs Sequential $PC+4$): $t_{\text{mux}} = 0.18\text{ ns}$.
4. PC Register Setup Time: $t_{\text{su\_pc}} = 0.15\text{ ns}$.

$$
t_{\text{target\_path}} = t_{\text{ibtb\_read}} + t_{\text{tag\_comp}} + t_{\text{mux}} + t_{\text{su\_pc}}
$$

$$
t_{\text{target\_path}} = 0.38\text{ ns} + 0.12\text{ ns} + 0.18\text{ ns} + 0.15\text{ ns} = \mathbf{0.830 \text{ ns}}
$$

##### Setup Timing Slack ($T_{\text{slack}}$) at $T_{\text{clk}} = 2.50\text{ ns}$:

$$
T_{\text{slack}} = T_{\text{clk}} - t_{\text{target\_path}} = 2.500\text{ ns} - 0.830\text{ ns} = \mathbf{+1.670 \text{ ns} \quad (POSITIVE SLACK!)}
$$

The target prediction path completes in **$0.830\text{ nanoseconds}$**, closing timing with $+1.670\text{ ns}$ of positive slack!

#### Step 2: Write the Synthesizable SystemVerilog Module

We construct `IndirectAndReturnPredictor` integrating the RSB and iBTB:

```systemverilog

    parameter int unsigned RSB_DEPTH   = 8,
    parameter int unsigned IBTB_ENTRIES= 64,
    localparam int unsigned TOS_BITS   = $clog2(RSB_DEPTH),   // 3 Bits
    localparam int unsigned IBTB_BITS  = $clog2(IBTB_ENTRIES) // 6 Bits
) (
    input  logic        clk,
    input  logic        reset_n,

    // IF Stage Interface
    input  logic [31:0] pc_if,              // Current PC in IF stage
    input  logic        is_call_if,         // 1 = Function Call (JAL/JALR rd!=x0)
    input  logic        is_ret_if,          // 1 = Function Return (RET)
    input  logic        is_indirect_if,     // 1 = Indirect Jump (JALR)
    input  logic [5:0]  ghr_if,             // 6-bit Global History Register
    output logic [31:0] target_pc_if,       // Predicted Target Address
    output logic        target_hit_if,      // 1 = Valid Target Hit

    // EX Stage Recovery Interface
    input  logic        ex_mispredict_flush,// 1 = Misprediction in EX stage
    input  logic [2:0]  ex_correct_tos      // Correct TOS pointer checkpoint
);

    // -----------------------------------------------------------------
    // 1. RETURN STACK BUFFER (RSB) LIFO ARRAY
    // -----------------------------------------------------------------
    logic [31:0] rsb_stack [0:RSB_DEPTH-1];
    logic [TOS_BITS-1:0] tos_ptr;

    // RSB Push & Pop Logic
    always_ff @(posedge clk or negedge reset_n) begin
        if (!reset_n) begin
            tos_ptr <= '0;
            for (int i = 0; i < RSB_DEPTH; i++) begin
                rsb_stack[i] <= 32'h0;
            end
        end else if (ex_mispredict_flush) begin
            // Restore TOS from committed checkpoint on pipeline flush!
            tos_ptr <= ex_correct_tos;
        end else if (is_call_if) begin
            // PUSH Return Address (PC + 4) onto RSB
            rsb_stack[(tos_ptr + 1'b1)] <= pc_if + 32'd4;
            tos_ptr <= tos_ptr + 1'b1;
        end else if (is_ret_if) begin
            // POP Return Address from RSB
            tos_ptr <= tos_ptr - 1'b1;
        end
    end

    logic [31:0] rsb_top_address;
    assign rsb_top_address = rsb_stack[tos_ptr];

    // -----------------------------------------------------------------
    // 2. INDIRECT BTB (iBTB) ARRAY (64 Entries x 57 Bits)
    // -----------------------------------------------------------------
    logic [56:0] ibtb_array [0:IBTB_ENTRIES-1]; // {Valid(1), Tag(24), Target(32)}

    // iBTB XOR Hash Indexing: PC[7:2] ^ GHR[5:0]
    logic [IBTB_BITS-1:0] ibtb_index;
    assign ibtb_index = pc_if[IBTB_BITS+1 : 2] ^ ghr_if;

    logic [23:0] if_pc_tag;
    assign if_pc_tag = pc_if[31:8];

    logic        ibtb_valid;
    logic [23:0] ibtb_tag;
    logic [31:0] ibtb_target;

    assign {ibtb_valid, ibtb_tag, ibtb_target} = ibtb_array[ibtb_index];

    logic ibtb_hit;
    assign ibtb_hit = ibtb_valid && (ibtb_tag == if_pc_tag);

    // -----------------------------------------------------------------
    // 3. MULTI-TIER TARGET SELECTION MULTIPLEXER
    // Hierarchy: RSB (Return) > iBTB (Indirect) > Default PC+4
    // -----------------------------------------------------------------
    always_comb begin
        if (is_ret_if) begin
            target_pc_if  = rsb_top_address; // Top of Return Stack!
            target_hit_if = 1'b1;
        end else if (is_indirect_if && ibtb_hit) begin
            target_pc_if  = ibtb_target;    // iBTB Target
            target_hit_if = 1'b1;
        end else begin
            target_pc_if  = pc_if + 32'd4;   // Default Sequential
            target_hit_if = 1'b0;
        end
    end

endmodule

`default_nettype wire
```

## Key Output Primitives

This lesson formally delivers the following conceptual primitives to your digital logic engineering toolbox:

* **Indirect Branch Target Buffer (iBTB)**: A path-history-indexed branch target cache that combines instruction addresses ($PC$) with global branch history ($GHR$) via XOR hashing to predict dynamic target addresses for polymorphic indirect jump instructions (`JALR`, virtual method calls, switch tables).
* **Return Stack Buffer (RSB / RAS)**: A dedicated hardware Last-In, First-Out (LIFO) stack that captures return addresses ($PC+4$) on function call instructions (`JAL`/`CALL`) and pops predicted return addresses on function return instructions (`RET`), achieving near $100\%$ branch target prediction accuracy for nested call structures.
